# ADR-315 — KPI variance normaliser ("Make this one")

Status: Accepted
Date: 2026-08-16
Related: ADR-270 (variant declaration), ADR-291 (group edit span), ADR-313 (bulk de-duplication)

## Context

The Performance Console groups KPI rows by structured title (ADR-270). Rows that
share the title but disagree on **description, formula, scoring logic or target**
are declared as separate *variants* — the amber "N variants" badge — instead of
being silently merged.

For "Power generation from 45 MWh/AFBC" (Jul 2026) the console showed 4 variants
of the same metric. Inspecting `bu_console_variant_key` inputs confirmed the
cause is field drift, not different metrics:

- description and formula swapped between columns on legacy imported rows,
- whitespace differences inside the scoring text,
- rows with the definition fields left empty.

Until now the badge only *reported* the split. Fixing it meant editing the group
definition once per variant, with no preview of how many employee rows each pass
would touch.

## Decision

Add an admin action **"Make this one"** on any KPI row with more than one variant.

1. The admin picks a canonical variant (default: the one covering the most
   employees, then most rows, then the most complete definition) and may edit the
   four definition fields before applying — this is how a swapped
   description/formula pair is corrected in one pass.
2. `variantNormalise.ts` (pure) builds one change set per variant, containing
   **only the fields whose normalised value differs**. Variants already aligned
   are reported as such and never written.
3. The rollout span reuses ADR-291 (`groupEditSpan.ts`): this month only, this
   and all future months, or next N months, with past months always excluded.
4. Preview dry-runs `bu_console_group_edit_definition` once per variant per
   target month and shows rows to write, rows skipped, and skip reasons.
5. Commit runs the same RPC without `dry_run`; each variant/month writes its own
   undoable `bu_console_edit_runs` row and the run stops on the first hard error.
   A typed `APPLY` confirmation is required.

## Invariants

- **Weightage is never written.** It is a legitimate per-employee number and is
  not part of the variant key. Normalising definitions must not flatten it.
- §88 immutability is unchanged: locked/approved rows keep being skipped unless
  the admin opts into "include rows already in review", and approved final
  scores are never touched.
- Rows with individual overrides stay exempt unless "align overrides" is on.
- No schema, RPC or RLS change — this is an orchestration layer over the existing
  group-edit RPC. Rollback = revert the UI; committed runs remain individually
  undoable.

## Consequences

The amber badge becomes actionable: an admin can collapse 4 variants to 1 with a
per-variant preview, and the same definition can be pushed forward into future
months in one action. Variance remains *declared* — the console still never
merges variants implicitly.

## Tests

`src/components/admin/bu-console/variantNormalise.test.ts` — 17 tests covering
canonical selection and tie-breaking, whitespace-insensitive matching, the
swapped description/formula case, change sets limited to differing fields, the
no-weightage invariant, NULL-on-empty writes, edited-canonical rewrites,
no-op detection and preview aggregation including failures.
