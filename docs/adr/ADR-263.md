# ADR-263 — BU Console Phase 5: Goal Objects and Roll-up

- **Status:** Accepted
- **Date:** 15 August 2026
- **Related:** ADR-259, ADR-260, ADR-261, ADR-262, POLICY §BU-CONSOLE-BETA, POLICY §88

## Context
The console can already navigate, write one value to many employees and advance
a group through each employee's own workflow. What it could not express is
*intent*: what the BU is aiming at, over which cycle, tracked how. The library
tables already carry the Peoplebox-shaped goal fields; they had no per-scope
instance to hang a target on.

## Decision
Add `public.bu_goals` — one goal per KPI definition per scope per period — plus
three SECURITY DEFINER RPCs (`bu_goal_list`, `bu_goal_upsert`,
`bu_goal_rollup`) and a Goals tab on `/admin/bu-console`.

- One object, an `entity_level` on it (org / BU / department / individual).
- `parent_goal_id` gives alignment without a rigid tree.
- Goal = a metric: start, target, current, unit, progress type.
- `tracking_method` is explicit (manual / rollup / source) so the future
  auto-feed is a value change, not a migration.
- `subperiod_summary_rule` (last / sum / avg) is stored, not inferred.

## What we did not take from the OKR model
- No 0–1.0 grading — scoring stays the per-employee 0–5 bands.
- No straight-average roll-up — aggregation is weightage-weighted.
- No second approval chain — approval stays the resolved per-employee workflow.

## Consequences
- **Positive:** targets become first-class and explainable (roll-up returns its
  per-period breakdown); no employee data is copied into the new table.
- **Negative:** one more table and a second place a "target" can live
  (goal target vs per-employee `kpis.target_value`); the beta does not reconcile
  them, it displays both.
- **Mitigations:** admin-only writes, feature flag, additive schema.

## Rollback
Drop `bu_goals` and the three RPCs. Review data, scores and workflows are
untouched by design.
