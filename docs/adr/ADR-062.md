# ADR-062 — Workflow Resolution Report uses a single client-side resolver

**Date:** 2026-05-11
**Status:** Accepted

## Context
The "Workflow Configuration Report" was an Excel export from `/admin/workflow-config` that listed only employees with explicit overrides. Employees relying on the default template were absent, and the user reported the report as "blank". There was also no on-screen surface to diagnose why a workflow stage (e.g. Skip-Level) resolved to N/A for a given employee + month.

## Decision
- Add a period-aware in-app **Workflow Resolution Report** at `/reports/workflow-resolution`.
- Introduce `src/lib/workflowResolver.ts` (`resolveChain` + `buildResolverContext`) as the **single source of truth** for the per-stage user chain.
- Template selection still flows through the canonical DB function `get_employee_workflow_info` (no client-side template logic).
- The existing admin export gains an additional "All Employees (Resolved)" sheet using the same resolver (global-only, since the admin page has no period selector).
- N/A is always paired with one of five typed reasons: `stage_not_in_template`, `no_manager_on_profile`, `skip_level_loop`, `resolved_user_inactive`, `role_unassigned`.

## Why not a DB function
The bulk RPC `get_bulk_employee_workflows` only returns `stages[]`. Resolving role-pool stages (HR PMS / Auditor / Management) needs `user_roles` joins that already happen on the client for other surfaces. Pushing this into SQL would duplicate logic without changing template selection, and would force every consumer to re-fetch role data anyway.

## Consequences
- POLICY §122 enforces the single-resolver rule on the client.
- Adding a new N/A reason requires updating the enum, label map, and at least one unit-test case in `src/test/workflowResolver.test.ts` in the same patch.
- The admin export's resolved sheet is global-only by design; period-specific resolution lives on the new report page.
