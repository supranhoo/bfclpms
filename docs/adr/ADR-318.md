# ADR-318: A KPI data-table row owns its period

## Status
**Accepted**

## Date
2026-08-26

## Context
A provider tried to load a full year of history for a bi-monthly KPI
("Power Gen 45MW AFBC", Jul-25 → Jun-26) into the Performance Console data
table and could not update any month — current or historical.

Two defects, one root cause:

1. `LedgerRowDialog` had no period control. It read `period`/`year` straight
   from the console header props and stamped every save with them. To enter
   twelve months the officer had to move the console header twelve times.
2. Worse, **editing** an existing historical row also re-stamped it with the
   header's month. Opening a Jul-25 line while the header sat on Aug-26 moved
   that line to Aug-26 — silent data corruption presented as "cannot update".

CSV import had the same flaw: `importCsv` ignored any date column in the file
and applied the header period to every line.

The backend was never the constraint — `org_kpi_dataset_row_save` accepts any
`(review_period, review_year)` and enforces no anchor-month rule. The limitation
was entirely in the UI.

## Decision
**A ledger row owns its period.** The console header is a default for new rows
only, never an override on save.

1. `LedgerRowDialog` gains Month + Year selectors. New rows default to the
   header; editing a row loads and preserves that row's own period.
2. A new `LedgerHistoryDialog` renders one fiscal cycle (Jul → Jun) as a
   12-line grid built from the KPI's own column design, with spreadsheet paste
   support. It is preview-first: a running new / updated / unchanged count is
   shown, and it commits through the audited bulk-import RPC with a dry run
   first. Blank months are never written.
3. CSV import parses `Month` / `Period` and `Year` columns per line via
   `parsePeriodToken` (accepts `Jul-25`, `July 2025`, `2025-07`, `07/2025`),
   falling back to the header only when a line carries no date.
4. Multi-month KPIs surface their cycle scope and anchor month through the
   canonical `buildCycleScopeLabel` helper in both dialogs; non-anchor months
   are shaded and labelled rather than blocked.

## Alternatives Considered

### Alternative A: Keep header-driven periods, add a "history mode" toggle to the console header
- **Description:** Leave the dialogs as they are and let the officer switch the
  whole console into a past month.
- **Rejected because:** It does not fix the corruption — editing a row would
  still re-stamp it — and it forces twelve context switches for one year of data.

### Alternative B: Server-side period inference from a formula column
- **Description:** Derive the period from a date column in the dataset schema.
- **Rejected because:** Dataset schemas are user-designed; not every KPI has a
  date column, and inference would silently disagree with the stored
  `review_period` used by scoring and fiscal-window guards.

### Alternative C: Free-text period entry
- **Description:** A single text box for "Jul-25".
- **Rejected because:** `review_period` must match the canonical month names
  used by `fiscalWindow` helpers and percolation; free text invites drift.

## Consequences

**Positive**
- Historical months are editable in place, without moving the console.
- A year of history is one paste instead of twelve dialogs.
- CSV files that already carry a month column import correctly.
- Multi-month KPIs explain their anchor rather than appearing broken.

**Negative / risk**
- The history grid loads both calendar years of the cycle when opened
  (two paged reads, gated on `historyOpen`).
- Providers can now write non-anchor months for a multi-month KPI. This is
  deliberate — legacy sheets sometimes carry them — and is signposted, not
  blocked.

**Guards**
- Fiscal pairing uses `isFiscalTuple` per `mem://architecture/pms/fiscal-window-guard`;
  no bucketing on `review_period` alone.
- Writes route through the existing bulk-import path, so reason capture, the
  change trail, and stale-validation marking all apply unchanged.
