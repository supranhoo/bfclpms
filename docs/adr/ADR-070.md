# ADR-070: Increment criterion_key bound to canonical metrics + fail-closed engine

- Status: Accepted (May 2026)
- Context: RCA on Vivek Kumar Dansena (employee 101784, AY 2025-26) showed a 20% increment despite Absent Days = 6 and an active "Absent > 0" ineligibility rule. The approved `increment_eligibility_criteria` rows stored `criterion_key` values `absent`, `lwp`, `discipline_action` — slugified from admin-edited criterion names. The engine's metrics map only exposes the canonical keys `absent_days`, `lwp_days`, `disciplinary_actions`, `training_compliance`, so every lookup returned `undefined` and the `continue` statement silently bypassed the rule.
- Decision:
  1. **Engine fails closed** — `supabase/functions/compute-increment/index.ts` now resolves each criterion's `criterion_key` against the canonical metrics map first, then a built-in alias table (`absent → absent_days`, `lwp → lwp_days`, `discipline_action → disciplinary_actions`, `training → training_compliance`, plus common variants). Unknown keys produce a `Configuration error: criterion '…' is not mapped to any input metric — contact admin` reason and mark the employee `ineligible`. Silent skips are no longer possible.
  2. **UI binds metric explicitly** — the Add/Edit Ineligibility Criterion dialog (`IncrementEligibilitySection.tsx`) now requires a "Metric" dropdown selection backed by `src/lib/incrementCriterionMetrics.ts` (`absent_days | lwp_days | disciplinary_actions | training_compliance`). The free-text criterion name is decoupled from the stored key, so renaming a rule can never break engine evaluation again. Editing a legacy row pre-resolves the key via the alias map and auto-corrects it on save.
  3. **One-time data fix** — a migration normalizes `increment_eligibility_criteria.criterion_key` for any existing row matching the alias table to its canonical value.
- Consequences: Future runs evaluate active ineligibility criteria correctly. Past `increment_run_items` rows are NOT rewritten (per the user's constraint). Misconfigured criteria now surface as an explicit Configuration-error reason instead of an undeserved increment. Rollback is reverting the touched files; the data migration is reversible by mapping canonical values back to whatever names were previously slugified, but the canonical state is the desired forward state.
