# ADR-044: Production Daily Entry Governance

## Status
**Accepted**

## Date
2026-03-31

## Context
Production-based incentive programs needed daily achievement tracking with per-ton rate calculations. The data entry model and rate resolution strategy needed to be defined.

## Decision (v2 — 2026-04-17)
Programs with per-ton production rates use daily achievement grids. Rate resolution follows strict priority: Employee > Department > BU > Company > Common, with company resolved via `profiles.company_id` first then dept→BU→division→company fallback (unified with slab matching). Daily values stored as JSONB in `production_daily_entries`. **Production incentive records are stored canonically per sub-period (`1-10`, `11-20`, `21-31`); `Full Month` is a derived UI aggregation, never a stored production row.** Recomputes purge legacy `Full Month` production rows. The edge function returns rich diagnostics (`employees_in_scope`, `employees_with_daily_entries`, `employees_with_resolved_rate`, `employees_skipped_no_rate`, `records_pre_scope`, `records_post_scope`) so empty results explain themselves.

## Alternatives Considered

### Alternative A: Monthly aggregate entry only
- **Description:** Enter a single monthly production total instead of daily values
- **Rejected because:** Loses granularity needed for period-based payment splits (1-10, 11-20, 21-31). Cannot audit daily performance patterns.

### Alternative B: Flat rate for all employees
- **Description:** Single production rate applied universally
- **Rejected because:** Different roles, departments, and BUs have different rate structures. A flat rate would be inaccurate for diverse workforces.

### Alternative C: Client-side incentive calculation
- **Description:** Calculate incentive amounts in the browser
- **Rejected because:** Client-side calculations are not authoritative — edge function must be the single source of truth for incentive amounts.

## Consequences

### Positive
- Granular daily tracking with flexible rate assignment
- Server-side computation ensures accuracy

### Negative
- Complex JSONB storage and rate resolution logic

### Neutral
- Detection priority: Vessel rates → Vessel grid; Production rates → Daily grid; Neither → Slab-based grid
