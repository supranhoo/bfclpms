# ADR-207 — PIP Trigger Suggestions & Policy Guardrails

**Status:** Accepted · **Policy:** §PIP-TRIGGER-SUGGESTIONS · **Date:** 2026-07-30

## Context

PIP Management (ADR-205) shipped with a working lifecycle but an empty list: there was
no way to discover *who* needs a plan. The reference experience already existed in
Reports → Monthly Scorecard → "Date Range (Trend)", which flags employees below the
configured threshold across a month range.

In parallel, several structural requirements of POLICY §15 had no enforcement point:
support & resources provided (§15.6), skip-level (RM2) sign-off before activation
(§15.5), employee acknowledgement (§15.9), no overlapping plans and duration/cadence
bounds (§15.7), and the 3-month post-PIP sustain window (§15.12).

## Decision

**Server.** `performance_improvement_plans` gains `support_provided`, `trigger_source`,
`trigger_context`, `rm2_approver_id` / `rm2_approved_at` / `rm2_remarks`,
`employee_acknowledged_at` / `employee_ack_comments` and `monitoring_until`.
`trg_pip_rm2_gate` blocks activation without skip-level sign-off; `pip_rm2_approve`
and `pip_acknowledge` are security-definer RPCs that force the acting user.
`trg_pip_stamp_monitoring` stamps the sustain window on completion, backed by the new
`pip_monitoring_records` table (RLS + grants + audit trigger).

**Rules SSOT.** `src/lib/pip/pipTriggerRules.ts` owns both triggers, the reason text,
candidate classification (eligible / live_pip / relapse_window) and the §15.7
duration + cadence validators. The monthly rule delegates to the existing
`pipCandidateRule.ts`, so the Suggestions tab and the Trend report cannot diverge.
`src/lib/pip/pipPolicySettings.ts` reads the configurable bounds.

**Annual rating derivation.** `annual_review_instances.final_rating` is a text
descriptor, so `usePIPCandidates` derives the comparable number from `total_score`
(0..100 by §AR-FINAL-SCORE-SCALE-INVARIANT) rebased to the 5-point scale.

**UI.** `PIPManagement` becomes two views — *PIPs List* and *Suggestions*.
`PIPSuggestionsPanel` shows per-month evidence, the annual rating, the matched
trigger, candidate state and a paginated, searchable, filterable grid. "Initiate PIP"
opens `PIPCreateDialog` prefilled with the employee and the policy-worded evidence
text, which then enforces duration, cadence and no-overlap before submit and persists
the trigger metadata. `PIPDetailSheet` surfaces support provided, the RM2 approval
action, employee acknowledgement and the post-PIP monitoring window.

## Consequences

- Suggestions are advisory only; plan creation stays a human act with a full audit trail.
- The threshold remains admin configuration; a divergence from the policy value of 2 is
  surfaced in the UI rather than silently overridden.
- Suggestions load only while the tab is active because the trend RPC is org-wide.

## Verification

`src/test/pip/pipTriggerRules.test.ts` — 20 tests covering both triggers, reason text,
candidate classification and the duration/cadence guardrails. Existing
`src/test/pip/pipLifecycle.test.ts` (18 tests) continues to pass.

## Amendment — anchored evaluation window (2026-07-30)

Monthly KRA review can lag by up to two months, so a trailing window that always
ends at "last month" judges employees on months that are not yet reviewed (blank
cells), and a blank month disqualifies the row. `trailingWindow` now accepts an
optional `anchor` — the last month the window covers — and `usePIPCandidates`
forwards it into the trend query key. `PIPSuggestionsPanel` exposes it as an
"Up to month" select listing the last 18 complete months (`recentMonthOptions`),
defaulting to the previous complete month so existing behaviour is unchanged.
The trigger rules themselves are untouched. Guard:
`src/test/pip/pipWindowAnchor.test.ts`.
