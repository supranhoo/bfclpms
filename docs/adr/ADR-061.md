# ADR-061: Scoped Org KPI editor renders from snapshot, not useProfiles

- Status: Accepted (May 2026)
- Context: After ADR-055/056 + the snapshot RPC rollout, admins on `/admin/org-kpi-data` saw Per-Employee KPI cards render the header badge ("1 employee") and N/A toggle but **no scoped entry table**, leaving no way to enter a value. RCA: `buildCardData` in `src/pages/admin/OrgKpiDataEntry.tsx` only built `scopedRows` when `allProfiles` (paged `useProfiles`) was loaded AND the mapped employee was in that result. The snapshot RPC now returns much faster than the paged profiles query, opening a race window where the editor was suppressed. RLS-hidden profiles produced the same symptom permanently.
- Decision: `buildCardData` now builds `scopedRows` from the snapshot's `mappedEmployeesMap` / `mappedDepartmentsMap` + `perEmployeeTargetMap`. `useProfiles` and `useDepartments` are used only to enrich display (full name, designation, department name); when an enrichment is missing we fall back to `Employee {id-prefix}` / `Dept {id-prefix}` so the row still renders and accepts input. The render gate in `OrgKpiEntryCard.tsx` was loosened to `data.scope !== 'organization' && !isNa` (no longer requires `data.scopeLabel`).
- Consequences:
  - The scoped entry editor appears immediately on page load.
  - Save / Propagate paths are unaffected — they key off `scopeId` (UUID), which the snapshot already supplies.
  - The existing amber "Showing X of Y mapped employees…" banner continues to explain RLS visibility gaps but no longer hides the editor.
- Tests: extend `src/test/orgKpiEmptyState.test.ts` family with a `buildCardData`-shaped regression covering snapshot-only rendering.
