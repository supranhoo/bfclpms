

# Fix "Open in App" Navigation for Query Resolved Notifications

## Problem

When clicking "Open in App" on a "Query Resolved" notification, users are taken to the home dashboard instead of the relevant KPI details. This affects query raisers (typically managers/reviewers) who receive these notifications.

## Root Cause

Two issues found:

**1. Missing employee context in navigation logic**

The `getNotificationNavigationPath` function determines if a notification is "self-targeted" by checking `metadata.employee_id`. For `query_resolved` notifications, the metadata only contains `query_id` and `resolution_notes` -- no `employee_id`. This causes the function to assume the notification is about the current user's own KPI, generating a self-view link (`/dashboard?kpi=xxx`).

But the KPI actually belongs to the employee (raised_to), while the notification recipient is the query raiser (a different person). The Dashboard only loads the current user's KPIs, so it can't find the linked KPI and falls back to showing the bare dashboard.

**2. Spurious notifications from send-back backfill**

The migration that added `query_type` changed send-back entries from `status = 'open'` to `status = 'resolved'`. This triggered the `notify_on_query_resolved` database trigger, creating "Query Resolved" notifications for items that were actually informational send-backs, not real queries.

## Changes

### Fix 1: Update navigation logic (`src/lib/inboxUtils.ts`)

For `query_resolved` and related notification types, use `related_user_id` (which stores the KPI owner's ID) to determine the correct employee context. When the notification recipient is not the KPI owner, build a team-view deep-link:

```
/dashboard?view=team&employee=<kpi_owner_id>&kpi=<kpi_id>&panel=queryHistory
```

This ensures the reviewer sees the employee's scorecard with the query history panel open.

### Fix 2: Update notification trigger condition (database migration)

Update the `notify_query_resolved` trigger to fire on ANY status change to `resolved` (not just `open` to `resolved`), so the two-step flow (`responded` to `resolved`) also generates notifications. Also add a guard to skip notifications for `send_back` type queries.

### Fix 3: Clean up spurious notifications (database migration)

Delete the false `query_resolved` notifications that were generated by the backfill migration for send-back entries.

### Fix 4: Update documentation (`DOCUMENTATION.md`)

Document the corrected navigation logic and trigger behavior.
