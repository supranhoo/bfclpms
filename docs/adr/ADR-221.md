# ADR-221: Annual Review eligibility criteria + exemption approval

- Status: Accepted (July 2026)
- Related: ADR-181 (eligibility report columns), ADR-212 (rating slabs), ADR-218/218a-e (Bell Curve), ADR-220 (calibration)

## Context

Eligibility answers already exist per instance (`annual_review_instances.eligibility_inputs`, questions authored on `annual_review_templates.sections.eligibility_criteria`), but the Bell Curve Analysis had no way to see who fails eligibility, and there was no governed way to waive an operational failure (attendance shortfall, LWP) without editing the underlying answer.

## Decision

1. **Master-data policy, not hardcoding.** `public.annual_review_eligibility_exemption_policy` holds `question_key -> is_exemptable`. Seeded so that *absent* / *lwp* / *leave without pay* are exemptable and *disciplinary* / *month completion* / *months of service* / *tenure* are not. Matching is substring-based on the normalised question name; **no matching row means not exemptable (fail closed)**.
2. **Exemption records.** `public.annual_review_eligibility_exemptions` (one row per instance + criterion) with `pending | approved | rejected`, reason, requester, decider and decision note. Unique on `(instance_id, criterion_id)`.
3. **Server-side guard.** `ar_elig_exemption_guard()` rejects any insert/update that requests or approves a non-exemptable criterion and blocks self-approval (except admin). `ar_eligibility_is_exemptable()` and `ar_can_approve_eligibility_exemption()` are SECURITY DEFINER helpers. RLS: reviewers/assistance-scope can read and request; only admin / hr_pms / management can approve, reject or revoke.
4. **Client SSOT.** `src/lib/annualReview/effectiveEligibility.ts` — `resolveEligibility()` returns `eligible | exempted | ineligible | unknown` plus `waived` / `blocking` failure lists. It reuses the ADR-181 evaluator so the report, the UI and the exports can never disagree.
5. **Slab effect (decision A).** An `ineligible` employee's increment slab is displayed as `0%` via `effectiveSlabPercent()`. Rating bands and the bell-curve distribution are unchanged — eligibility is an overlay, not a re-rating.
6. **UI.** Bell Curve Analysis gains an **Eligibility** filter (Eligible / Exempted / Ineligible / Not assessed) and an **Ineligible** KPI card. The heat map drill-down gains an Eligibility badge column, the eligibility column in its CSV, and an **Exemption** action (`ExemptionDialog`) for admin / HR PMS / management.

## Consequences

- Purely additive schema; rollback = drop the two tables and the three functions, revert the touched client files.
- Templates without eligibility criteria resolve to `unknown` and render an em-dash, so nothing changes for cycles that never used eligibility.
- Guard: `src/test/annualReview/effectiveEligibility.test.ts` (9 cases).
