# ADR-060 — Org KPI: data-owner profile RLS + FK save guard

Status: Accepted (May 2026)

## Context
A registered Org KPI data owner (e.g. Ankan, KPI = "Completion of Mandated
Training Hours") saw the propagation preview report **50 employees will
advance** while the scoped entry table only rendered **25 rows**, and saving
failed with `org_kpi_values_employee_id_fkey`.

Why the two surfaces disagreed:
- `preview_org_kpi_propagation` is `SECURITY DEFINER` ⇒ sees all 50 mapped kpis.
- `useProfiles()` reads `public.profiles` under RLS. The data owner had no
  policy granting visibility to *every* employee mapped to a KPI they own —
  only to other registered data-owner profiles. The page silently
  intersected 50 mapped IDs with 25 visible profiles.

Why the save crashed:
- `handleCardSave` trusted the in-memory `scopeId` and posted it straight to
  `org_kpi_values.employee_id`. A stale or hidden UUID failed the FK to
  `profiles(id)` with no user-friendly fallback.

## Decision
1. **DB**: add `public.is_org_kpi_data_owner_for_profile(uuid)` and a new
   profiles SELECT policy `Org KPI data owners can view their mapped employee
   profiles`. Owners now see exactly the employees mapped to KPIs they own —
   no broader, no narrower.
2. **Frontend**: in `OrgKpiDataEntry.handleCardSave`, split the upsert payload
   into `{ safe, orphans }` against the live `allProfiles` set. Surface a
   single toast for orphans instead of letting the FK error bubble up.
3. **UX**: when `scopedRows.length < employeeCount`, render an amber banner in
   `OrgKpiEntryCard` so the dialog/table mismatch can never be silent again.

## Consequences
- Data owners can both see and submit values for every mapped employee.
- Other roles' visibility is unchanged.
- Any future RLS regression manifests as a visible banner + a precise toast
  rather than a raw Postgres error.

## Tests
- `src/test/orgKpiSaveOrphanGuard.test.ts` locks the split predicate.
