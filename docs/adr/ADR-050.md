# ADR-050: Safety Manual-Fetch & Pagination

## Status
**Accepted**

## Date
2026-04-29

## Context
Safety list pages (incidents, permits, audits, audit log, training, assets, drills, contacts, hours-worked, users, SLA monitor) all auto-fetched on mount, several of them pulling unbounded result sets and filtering client-side. This caused slow cold loads, wasted Postgres reads, and degraded UX as datasets grow. The PMS side has accumulated similar costs over time; we want the Safety module — which is still young — to lock in a better policy *before* it bloats.

## Decision
Adopt a single, binding UX rule for every Safety list/query surface:
1. **Filters-first**: list pages render only the filter bar and an "awaiting search" empty state on mount. No data fetch fires.
2. **Click-to-load**: a single primary **Search** button (or Enter key inside any filter) triggers exactly one query.
3. **Paginated server-side**: every tabular surface paginates via `.range(from,to)` with `count:'exact'`; default 25, options 25/50/100.

We codify this as **POLICY.md §113** and ship four sanctioned primitives — `useManualQuery`, `<SafetyFilterBar>`, `<SafetyDataTable>`, `<SafetyEmptyState>` — that any future Safety list MUST consume.

## Alternatives Considered

### Alternative A: Keep auto-fetch, add infinite scroll
- **Description:** Page on scroll instead of an explicit Search.
- **Rejected because:** Still issues an immediate cold-load query, hides the cost from the user, and accessibility/printing/export workflows degrade with infinite lists.

### Alternative B: Auto-fetch with hard `LIMIT 25`
- **Description:** Always fetch first page automatically.
- **Rejected because:** For audit-style screens (incidents, audit log), the first 25 are rarely what the user wants; they almost always need filters. Auto-fetching just wastes the round-trip and trains users to ignore filters.

### Alternative C: Per-page opt-in (no module-wide rule)
- **Description:** Let each page author choose.
- **Rejected because:** Inconsistency is the exact bug we are trying to prevent. The whole point is a contract every future contributor inherits.

## Consequences

### Positive
- Cold-load of `/safety/*` list pages drops to a single render with no DB round-trip.
- Datasets can grow to millions of rows without affecting UX.
- One reusable filter/table contract — easier reviews, smaller diffs.
- Mutations are deterministic: they re-run the *last submitted* query, not a different shape.

### Negative
- Existing users must click Search to see lists they previously saw on mount. Mitigated by clear empty-state copy ("Apply filters and click Search to load data") and Enter-to-submit.

### Neutral
- Detail pages, dashboard tiles, and single-aggregate views are exempt and continue to auto-load.
