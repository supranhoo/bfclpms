# ADR-257 — Rollback requests require a predecessor stage

## Date
2026-08-14

## Status
Accepted

## Context
Binay Singh (102013), July 2026, KPI "Inventory Compliance to min max levels"
(`3f2e7c0b-98ec-4805-8d09-0ed16fa6c13e`) was reset by an admin on 15 Jul
(`ADMIN_FULL_RESET`), moving it back to `kra_set` — the first workflow stage —
and clearing the self score.

"Request Rollback" was still offered on that KPI. `resolvePreviousStatus`
returned null (no stage precedes `kra_set`), and the hook surfaced the internal
message "Cannot determine rollback target status".

Verified during RCA: July 2026 is at stage `planning`, is not locked, and has no
employee/department/role locks — the period governance layer was NOT involved.

## Decision
- New pure SSOT `src/lib/rollbackEligibility.ts`:
  `isFirstWorkflowStage()`, `canRequestRollback()`, `FIRST_STAGE_ROLLBACK_MESSAGE`.
  Resolution prefers the KPI's resolved workflow stages and falls back to the
  canonical status list when the stages are stale/empty.
- `useCreateRollbackRequest` rejects first-stage requests up front with the
  plain-language message instead of the internal one.
- `UnifiedScorecard` and `SelfReviewSheet` hide the "Request Rollback" button
  when the KPI is at the first stage (a sent-back KPI already IS the rollback
  outcome). `RollbackRequestDialog` re-checks on submit so a stale render cannot
  create an impossible request.
- Self-review sheet shows "Awaiting your self-review for <period>" on
  first-stage KPIs with no prior submission, so an editable row is not mistaken
  for a locked one.

## Consequences
- No dead-end rollback action; the impossible case is removed rather than
  error-handled after the fact.
- Rollback remains available from every stage that has a predecessor.
- Frontend/validation only — no schema, RLS or data changes; fully revertible.
