# ADR-336 — Performance Console: unified KRA / KPI / employee search

**Status:** Accepted · 2026-09-01

## Context

The console scope toolbar offered period + four org filters and nothing else.
Once a scope loaded, finding one KRA, one KPI or one person meant scrolling the
category strip, the KRA list and a 100-row people page by eye. Large BUs load
hundreds of KPI rows and thousands of mapped employees, so the surface was
effectively unsearchable.

## Decision

1. **Tree search is client-side.** `bu_console_tree` already returns the whole
   category → KRA → KPI structure for the applied scope in one read, so the new
   toolbar search box is a pure projection over that payload
   (`consoleSearch.ts` → `filterConsoleTree`). No new RPC parameter, no extra
   round trip, no change to how the tree is fetched.
   - A category-name hit keeps the whole category.
   - A KRA-name hit keeps that KRA with all of its KPIs.
   - Otherwise only KPIs matching title, legacy `kpi_name`, description or a
     variant name survive; emptied KRAs and categories are dropped and node
     counts are recomputed so nothing advertises hidden rows.
   - The drilldown re-anchors on the first surviving category + KRA, so the
     user never lands on a category the filter has emptied.

2. **People search is server-side.** The people strip is paged
   (`PAGE_SIZE = 100`), so filtering in the browser would only search the open
   page. `public.bu_console_run_snapshot` gains
   `p_search text DEFAULT NULL` matching `profiles.full_name` /
   `profiles.employee_code` (`ILIKE`), applied inside both scope CTEs so the
   totals, the page window and the cell payload agree.

3. **One vocabulary, two scopes of effect.** The toolbar query also seeds the
   per-KPI "Find person" box (`initialPersonSearch`), so typing an employee
   name once filters both the tree and the people list of any KPI opened
   afterwards. The toolbar result line states this explicitly.

4. **Debounced (POLICY §120).** Both inputs pass through
   `useDebouncedValue(value, 300)` before feeding a `useMemo` or a query key.

## Consequences

- Additive and reversible: `p_search` defaults to NULL, so every existing
  caller behaves exactly as before. Rollback = revert the function to the
  11-argument body and drop the two UI props.
- No schema change, no data written, no scoring or workflow path touched.
- Scalability: tree filtering is O(nodes) over already-loaded data; people
  search narrows the SQL scope *before* paging, so it reduces work rather than
  adding it.
- Tests: `src/components/admin/bu-console/consoleSearch.test.ts` (7 cases —
  empty query passthrough, KPI hit with recomputed counts, KRA hit, category
  hit, description/variant hits, no-match).
