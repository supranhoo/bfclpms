# ADR-040: Single-Source Query Raised Notifications

## Status
**Accepted**

## Date
2026-03-30

## Context
Query raised notifications were being created from both frontend code and a database trigger, causing duplicates with inconsistent metadata keys.

## Decision
`query_raised` notifications must only be created by the database trigger `notify_on_query_raised()` on the `kpi_queries` table. Frontend code must NOT insert duplicate notification records. The trigger uses `jsonb_build_object('query_id', NEW.id, 'query_reason', NEW.reason)`.

## Alternatives Considered

### Alternative A: Dual insert from frontend + trigger
- **Description:** Keep both frontend and trigger creating notifications
- **Rejected because:** Causes duplicate notifications and inconsistent metadata keys (e.g., `reason` vs `query_reason`), leading to email templates receiving null values.

### Alternative B: Frontend-only notification creation (remove trigger)
- **Description:** Handle all notification creation in the React mutation hooks
- **Rejected because:** Frontend-only creation is bypassable (direct API calls, admin tools) and less reliable. Server-side triggers guarantee notifications for every query regardless of entry point.

## Consequences

### Positive
- Zero duplicate notifications
- Consistent metadata structure for email templates

### Negative
- Frontend developers must remember NOT to add notification inserts for queries

### Neutral
- Pattern can be extended to other notification types
