# ADR-338 — KPI rename lock predicate uses the review_status vocabulary

Status: Accepted (2026-09-01)

## Context
"Preview rename" in the group definition editor failed with
`invalid input value for enum review_status: "locked"`.

`public.kpis.status` is of enum type `review_status`
(`kra_set, self_review, manager_check, functional_manager_check, audit,
approved, management_review, skip_level_check, hr_pms_review`). The ADR-334
rename functions compared it to `'locked'` and `'approved_by_manager'`, which
belong to the unrelated `kpi_status` enum. Postgres rejects the literal at
execution time, so `preview_kpi_range_correction` always raised, and
`correct_kpis_range` would raise on any "skip locked rows" apply.

## Decision
Both functions adopt the canonical console lock rule already used by
`bu_console_group_edit_definition`:

> a row is locked when `review_submissions.final_score IS NOT NULL`
> or its `status` has moved past `kra_set`.

- `preview_kpi_range_correction` counts `locked_rows` with that predicate via a
  `LEFT JOIN public.review_submissions`.
- `correct_kpis_range` gates `p_include_locked` on the same predicate, computed
  once in a `scoped` CTE so preview counts and apply behaviour agree.

Signatures, grants, `SECURITY DEFINER` and `search_path` are unchanged; no
client change was needed.

## Consequences
Rename preview returns rows instead of erroring, and the "N locked rows" badge
shows a real count. Regression test:
`src/tests/kpiRenameLockPredicate.test.ts`.
