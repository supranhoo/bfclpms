# ADR-256 — Evidence read access must equal KPI row visibility

- **Date:** 2026-08-13
- **Status:** Accepted
- **Supersedes/extends:** ADR-190 (evidence read by KPI participation), ADR-250 (streamed preview + transient errors)

## Context

Users opening a KPI evidence attachment (e.g. `201133_Continuous_monitoring_of_budget_and_cost_Self_Evidence.xlsx`) saw
**"You do not have access to this file, or it is no longer available."**

Verified before changing anything:

- Every evidence object referenced by that employee's submissions **exists** in the private `review-evidence` bucket.
- Across all `review_submissions`, every self-evidence URL carrying a KPI id resolves to an existing KPI (0 orphans) and
  **0** point at a KPI owned by a different employee — so the KPI owner is never denied by a path mismatch.
- The failure is therefore Storage authorisation: `createSignedUrl` is refused and the client normaliser maps a 400/404
  denial to the access-denied wording.

Two rules governed the same evidence and disagreed:

| Question | Predicate |
| --- | --- |
| Can I see the KPI row and its attachment chip? | `public.can_view_kpi_row()` |
| Can I open the attached file? | `public.can_read_kpi_evidence()` |

`can_view_kpi_row` granted owner, admin, auditor, hr_pms, **management**, report-access override, manager,
**skip-level manager via `get_skip_level_manager`**, mention access and **org-KPI data owners**.
`can_read_kpi_evidence` granted only owner, direct manager, manager-of-manager, assigned auditor and mention access.
The legacy policy `Users can view authorized evidence` patched admin/auditor/hr_pms back in, which is why the defect
looked intermittent.

Uncovered viewers: **management role, resolved skip-level manager, functional manager (`profiles.functional_manager_id`,
ADR-193), org-KPI data owners, report-access overrides.**

### 5 Whys

1. Storage refused the signed-URL request.
2. `can_read_kpi_evidence()` returned false for the viewer.
3. Its participant set was narrower than KPI-row visibility.
4. It was authored for ADR-190 and never re-synced when management / functional-manager / skip-resolver visibility landed.
5. No parity test existed, and the error text labelled every denial "no access", hiding the real cause.

## Decision

1. `can_read_kpi_evidence(uuid)` is rewritten (`STABLE SECURITY DEFINER`, `search_path = public`) to mirror
   `can_view_kpi_row`: owner, admin, auditor, hr_pms, management, report-access override, reporting manager,
   functional manager, manager-of-manager, resolved skip-level manager, assigned auditors (employee and KPI level),
   mention access, org-KPI data owner. Anonymous callers are denied.
2. Storage policies are unchanged — they already delegate to the helper, so all prefixes
   (self / reviewer / auditor / management / observation / observation-replies) are fixed in one place.
   The ADR-190 invariant (never drop the folder-owner policy without recreating it) is preserved.
3. The preview dialog logs the bucket, path, KPI id and real storage status on a signing failure while still showing the
   normalised message; the ADR-250 transient-busy branch is untouched.
4. Regression guard `src/test/review/evidenceReadParity.test.ts` fails if the helper stops covering any relationship or
   role that grants KPI-row visibility.

## Consequences

- Additive only: no one loses access, no rows change, the bucket stays private.
- Exposure is bounded to users who already see the KPI, its scores and the attachment chip.
- **Rollback:** one migration re-creating the previous `can_read_kpi_evidence` body.
