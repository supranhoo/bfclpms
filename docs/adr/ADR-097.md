# ADR-097 — Auto-Advanced Self Snapshot Refresh on OKV Re-propagation

- **Date:** 2026-06-29
- **Status:** Accepted
- **Related:** ADR-048 (auto-advance scoring), ADR-088, ADR-091, ADR-092 (snapshot fallback coalesce), POLICY §88 (Submission Snapshot Immutability), §88.5 (this carve-out)

## Context

Reported by Upendra/Biswajit (2026-06-29) for S.Lingamurthy Raju / "Asset Availability & Reliability" / May 2026: the Manager Review dialog showed `Value: 98.04 · Rating: 4` on the Self card while the System Auto-Advanced banner was visible and the Org KPI Value had been corrected to `99.61`. The remarks line ("99.61 details attached") confirmed re-propagation had run, but the snapshot columns were stuck at the original stub value.

Forensic trace:

1. Admin entered an early OKV of `98.04` for May 2026 and propagated.
2. ADR-048 auto-advance ran for the employee KPI: `review_submissions.self_score = 4`, `auto_advance_reason = 'Scored by Admin on behalf of self'`, `self_evidence_url(s) = NULL`, `kpis.status` advanced past `self_review`.
3. Admin corrected the OKV to `99.61` and re-propagated.
4. `propagate_org_kpi_value` evaluated `v_allow_overwrite` under `pre_review_only` policy — `current_status NOT IN ('kra_set','self_review')` — and skipped the row with `reason: 'reviewer_locked'`. The snapshot columns stayed at `98.04` / Rating 4 while `self_remarks` (no immutability guard) updated to the new value, producing the inconsistent display.

## Decision

Add a narrow §88.5 carve-out: re-propagation MAY refresh the Self snapshot (`achieved_value`, `self_achieved_value`, `self_score`, `self_rating`) on child rows that are *auto-advanced stubs* — `auto_advance_reason IS NOT NULL` AND `final_score IS NULL` AND no employee `self_evidence_url(s)`. Status, reviewer columns, and the step-back logic are untouched. Every refresh writes a `kpi_audit_logs` row (`action = 'OKV_AUTO_ADVANCED_RESYNC'`, `performed_by = NULL`, metadata carrying both values and the admin who triggered it).

The Self card in `ReviewStageCard.tsx` now renders an italic *"Will re-sync from Org KPI on next propagation"* hint whenever the row qualifies, so admins know what the next propagation will do.

## Alternatives Considered

### A. Blanket overwrite of Self snapshot on every re-propagation
- Description: drop the §88 guard entirely for `pre_review_only`.
- Rejected: violates POLICY §88 / HR audit law. Employees who actually self-submitted would have their values silently rewritten by an admin OKV edit, with no record of their original input.

### B. Admin-only manual `resync_org_kpi_snapshot(scope_id, period, year, reason)` RPC (ADR-092 deferred follow-up #3)
- Description: require an explicit one-off RPC to force the refresh per scope.
- Rejected for this fix: introduces a second admin surface for what the existing propagation path already does in 99% of cases; the symptom is "I corrected the OKV and re-propagated — why is the snapshot still stale". For non-stub rows the manual RPC is still the right tool and remains a separately tracked follow-up.

### C. Clear `auto_advance_reason` after first manager edit so the carve-out auto-narrows
- Description: have manager scoring clear the `auto_advance_reason` so subsequent re-propagation skips the row.
- Deferred: a desirable invariant in its own right, but orthogonal to this bug — even without it, the gating predicate already excludes rows once `final_score` is set, and reviewer columns are deliberately not touched.

## Consequences

### Positive
- Stale stub snapshots refresh automatically the next time the Admin re-propagates an updated OKV.
- Audit trail (`OKV_AUTO_ADVANCED_RESYNC`) makes the refresh fully traceable, including the human who triggered it.
- Real employee submissions (`self_evidence_url(s)` non-empty) and approved rows stay frozen — POLICY §88 invariants preserved.

### Negative
- A manager who already scored against the stale stub will see the Self value change beneath their score. Their own score is preserved, but they may want to re-score; the existing Bulk Sign-off / per-stage flows handle that.

### Neutral
- One extra `SELECT` per child row inside `propagate_org_kpi_value` to read `auto_advance_reason` / `final_score` / `self_evidence_url(s)`. Same row count as before; negligible overhead.

## Tests

- `src/test/review/propagateAutoAdvancedResync.test.ts` — five cases: (1) auto-advanced stub + not-approved → refresh + audit; (2) auto-advanced + final_score set → skip; (3) employee-submitted (`self_evidence_urls` non-empty) → skip; (4) `kra_set` row → still follows the original path; (5) resolver (`resolveSelfAchievedValue`) consumes the refreshed `self_achieved_value` and reports `pristine`.

## Rollback

Revert `public.propagate_org_kpi_value` to its pre-§88.5 body. Pure read fallout (the UI hint, audit-config entry) is additive and harmless if left in place, but the recommended order is: revert the function, then revert the four UI / docs files.
