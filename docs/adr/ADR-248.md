# ADR-248 — Multi-month KRA rollout & auto-rollover guardrails

## Date
2026-08-05

## Status
Accepted

## Context
Two gaps in KRA rollover:

1. The Rollover dialog only ever targeted a single month, so issuing a KRA set
   for a quarter or a full assessment period meant repeating the run manually.
2. The monthly cron deduped purely on `(kra_name, kpi_name, period)`. In June,
   11 employees had their July KRAs issued manually with a deliberately reduced
   KPI set. On 1 July the cron treated every removed KPI as "missing" and
   re-added it — 110 rows, pushing 5 employees past 100 total weightage.

Dedup cannot distinguish "period never prepared" from "period prepared, KPI
dropped on purpose". Intent has to be recorded explicitly.

## Decision
- Target resolution moves to a single pure module `src/lib/rolloverTargets.ts`
  (`single` / `next_n` / `rest_of_fy` / `full_fy`, July–June fiscal year, capped
  at `MAX_ROLLOUT_PERIODS`). The dialog dry-runs and applies each period in
  ascending order and shows a per-period plan table.
- New table `kra_period_issuance` marks a period as deliberately issued for an
  employee. Manual/admin rollovers write it automatically.
- `auto-rollover-kpis` skips issued employees when `triggered_by = 'system'`
  and `force` is false, with a backstop for employees who already have KPIs in
  the exact target month. Manual runs are never blocked.
- After insert, the function recomputes total weightage per affected employee
  and returns `weightage_warnings`; the UI shows them as an amber alert.

## Consequences
- Deliberate KRA reductions survive the next cron run.
- Weightage drift is visible at the moment it is created instead of at review
  time.
- Multi-month issuance is one run; each period stays independently auditable.
- Risk accepted: the backstop means the cron will not top-up an employee who
  holds any KPI in the target month — that top-up is now an explicit manual run.
