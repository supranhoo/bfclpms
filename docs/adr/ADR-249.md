# ADR-249 — Development Report captures What / Why / How

## Date
2026-08-04

## Status
Accepted

## Context
The Development Report (`/reports/dev-report`, POLICY §131) recorded only *what*
was built (title + description). Reviewers and auditors could not tell why a
change was made or how the delivered capability is used, so every entry needed a
verbal walkthrough to be meaningful as evidence.

## Decision
Every entry carries two additional, optional, genuinely-sourced fields:
- `rationale` (Why it was built) — ADR `## Context` / `## Problem`, changelog
  bullets labelled `**Why:** / **Problem:** / **Root cause:**`, or the migration
  header comment.
- `usage_notes` (How it is used) — ADR `## Consequences` / `## Usage`, changelog
  bullets labelled `**How:** / **Usage:** / **Impact:**`, or derived from the
  tables/functions a migration creates.

Rules:
- Fields stay NULL when no genuine source section exists — no invented text.
- `dev-report-ingest` fills the fields only when the stored value is empty, so
  admin-authored detail is never overwritten by a resync.
- XLSX export appends `Why It Was Built` / `How It Is Used` AFTER the locked
  101785 evidence columns, preserving backward compatibility.

## Consequences
- Report rows expand in the UI to show Why / How plus ADR and artefact refs.
- A "Detail coverage (Why + How)" KPI card shows how complete the evidence is.
- Admins can author or correct both fields from the add/edit dialog.
