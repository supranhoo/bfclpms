# ADR-309 — KPI Data Ledger (the data table behind a central KPI number)

Status: Accepted — 2026-08-21
Supersedes: nothing. Extends ADR-301 (central approval ladder) and ADR-302 (console UI).
Policy: POLICY §CONSOLE-KPI-DATA-LEDGER

## Context

Central approval (ADR-301/302) carries exactly one number per KPI per period:
`org_kpi_values.achieved_value`. Business users maintain the workings behind that
number in Excel — e.g. the CLU "Production" sheet with one row per month carrying
Target, Achieved, Achievement %, Prod Incentive and Rating, and the CPP
"Power Gen 8MW" sheet with the same shape but different columns.

Those sheets are the evidence for the headline number, and today they live outside
the system. When Audit asks "how did 92.77% arise", the answer is an attachment.

Two hard constraints shaped the design:

- The shape differs per KPI. Hardcoding Production columns would violate the
  zero-hardcoding rule and force a code change for every new KPI.
- The rows are not all equally visible. An employee must see their own slice, not
  the whole organisation's ledger.

## Decision

Every central KPI may carry its own **dataset**: an admin-configured table whose
columns, roll-up rule and scope are data, not code.

### Schema

| Table | Purpose |
| --- | --- |
| `org_kpi_dataset_defs` | One per KPI. Holds title, roll-up rule, value/target/weight column keys, scope mode. |
| `org_kpi_dataset_columns` | The column schema: key, label, data type (`number`, `text`, `percent`, `currency`, `date`, `select`, `formula`), required flag, `editable_by`, sort order, optional `formula`. |
| `org_kpi_dataset_rows` | The data. `values` is JSONB keyed by `column_key`; org scope is carried in real FK columns (`division_id`, `business_unit_id`, `department_id`, `location_id`, `level_id`, `pms_grade_id`, `employee_id`) so RLS can reason about it. |
| `org_kpi_dataset_row_history` | Append-only before/after of every row write, with actor and revision. |
| `org_kpi_dataset_validations` | One live audit sign-off per dataset/period. Re-validation invalidates the prior verdict rather than mutating it. |

### Access

`can_read_kpi_dataset_row` (SECURITY DEFINER): Audit / Management / HR PMS / admin
see everything; data owners and ladder step holders see their assigned scope;
an employee sees rows whose scope resolves to them or is unscoped for their unit.
`can_write_kpi_dataset` limits writes to the KPI's provider, its data owners and
admins. Both are used by RLS and by the RPCs, so there is one rule, not two.

### RPCs

`org_kpi_dataset_get`, `org_kpi_dataset_upsert_def`, `org_kpi_dataset_rows_read`
(server-side paged, `{rows, total, limit, offset}`), `org_kpi_dataset_row_save`,
`org_kpi_dataset_row_delete`, `org_kpi_dataset_bulk_import` (dry-run first),
`org_kpi_dataset_rollup`, `org_kpi_dataset_validate`,
`org_kpi_dataset_validation_state`.

`EXECUTE` is revoked from `PUBLIC` and `anon` on all of them and granted to
`authenticated` and `service_role` only.

### Roll-up

`org_kpi_dataset_rollup` derives the headline from the rows: `sum`, `sum_ratio`
(sum(value)/sum(target)×100), `avg`, `weighted`, `last`, `max`, `min`. It returns
its own working (`sum_value`, `sum_target`, `row_count`, a human note) so the
number is never unexplained. A zero denominator returns `null` with a reason
instead of a fabricated figure. `src/lib/review/kpiLedgerModel.ts` mirrors the
same arithmetic client-side for live preview; the server value is authoritative.

Formula columns are evaluated by a restricted arithmetic evaluator — identifiers,
numbers, `+ - * / ( ) .` only. Anything else, or a missing input, yields `null`.

### UI

`KpiLedgerPanel` mounts inside `KpiDetailDrawer` beneath the ADR-302 central
panel: paged grid, live roll-up with working, exception flags (missing required
value, no value, zero target, implausible achievement, duplicate period+scope),
CSV export/import with dry-run, and the audit validation rail.
`DatasetSchemaDialog` is the admin column designer; `LedgerRowDialog` is
single-row entry with live formula calculation.

## Consequences

- A new KPI sheet is a configuration exercise, not a release.
- Every headline number is now traceable to rows, and every row edit to an actor.
- Datasets are optional. A KPI without one behaves exactly as before ADR-309.

## Verification

- `src/components/admin/bu-console/kpiLedgerModel.test.ts` — 18 tests over
  parsing, formula safety, all seven roll-up rules, exception detection,
  formatting, scope labelling and validation liveness.
- Live signed-in run against a temporary dataset (two CLU Production rows,
  Jul-2025): `org_kpi_dataset_rows_read` returned `total: 2`,
  `org_kpi_dataset_rollup` returned `92.77` with working
  `sum_value 10580 / sum_target 11405`, `org_kpi_dataset_validate` recorded the
  sign-off and `org_kpi_dataset_validation_state` read it back. Smoke data removed.
