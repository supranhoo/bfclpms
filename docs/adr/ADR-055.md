# ADR-055: Fact-based Org KPI tile status

- Status: Accepted (May 2026)
- Context: The Org KPI Data Entry tile chip ("Pending / Entered / Propagated / Stuck") was derived only from `org_kpi_values.status`. When OKV.status was stale (`draft` / `sent_back` from earlier flows) but every mapped child KPI had already advanced past `kra_set`, the tile said "Entered" while the Propagate dialog said "0 will advance — reviewer-locked". Two surfaces, two truths.
- Decision: `getKpiStatus` in `src/pages/admin/OrgKpiDataEntry.tsx` now combines OKV state with the real per-employee `kpis.status`. If `mappedEmpIds.size > 0 && kraSetEmpIds.size === 0` (every child has already advanced), the tile is `'propagated'` regardless of OKV.status. The "stuck" / "entered" / "pending" semantics are otherwise unchanged. `useOrgLevelKpisWithEmployees` now also returns `mappedEmpIdsByKey` to support this.
- Consequences: tile chip now matches what the Propagate preview reports. No DB change; OKV row backfill is an opt-in Data-Repair action (out of scope here).
- Tests: `src/test/orgKpiTileStatus.test.ts`.

## 2026-05-11 follow-up — cross-scope chip parity

- The original decision applied only to the `'organization'` scope branch of `deriveOrgKpiTileStatus`. The `'employee'` and `'department'` branches kept an early `return 'pending'` whenever no OKV row carried a value, which produced a fresh "1 Pending" vs "34 propagated / 0 not propagated" drift on the Cost Management & Optimization card (Adherence to Manning Norms).
- Fix: the same `everyChildAdvanced` override now runs in the employee/department branches before the empty-`matching` early return. When `mappedEmpIds.size > 0 && kraSetEmpIds.size === 0`, the tile is `'propagated'` regardless of OKV presence — bringing the category chip into agreement with `deriveScopedRowStatus` and the per-row "X propagated / Y not propagated" summary.
- Regression: `src/test/orgKpiTileStatusChipParity.test.ts` (employee + department, OKV-empty and value-less variants).
