# ADR-215 — Change History capture completeness and uncapped export

Date: 2026-07-31
Status: Accepted

## Context

Two complaints about the Master Change History report:

1. **A reporting-manager change did not appear.**
2. **The Excel export stops at 5,000 rows.**

Database verification:

- ADR-213 created `public.log_profile_identity_change()` — a 21-field logger
  covering `reporting_manager_id`, `functional_manager_id`, `department_id`,
  `designation`, grade, level, location, DOJ, mobile, portal access — **but the
  migration never attached it to `public.profiles`.**
- `profiles` still ran `trg_profiles_identity_audit`, whose function logged only
  `full_name`, `employee_code`, `email`, `is_active`.
- `system_audit_logs` therefore held **0 rows** of `profile.field_changed` and 24
  rows of the legacy `profile.identity_changed`. The report's read path was
  correct; the write path did not exist. No manager change was ever captured.

The 5,000 figure was a client-side constant, not a server limit: the RPC pages
at 500 rows and returns the true filtered count.

## Decision

1. Drop `trg_profiles_identity_audit` and its 4-field function; bind
   `trg_profiles_field_audit AFTER UPDATE ON public.profiles` to the 21-field
   logger, so there is exactly one capture path.
2. Add a `reporting_org` category in `get_change_history` for
   `reporting_manager_id`, `functional_manager_id`, `department_id`,
   `designation`, mirrored client-side by `categoryForField`. Value resolution
   to names was already handled by `resolve_change_value`.
3. Raise `CHANGE_HISTORY_EXPORT_CAP` from 5,000 to 100,000 and reframe it as a
   runaway guard: the export loop now terminates on a short page, so a normal
   extract is complete. `truncated` is true only when the guard actually fires
   below the reported total.
4. Report real progress ("Exporting 12,400 of 38,910…") during the export.
5. State the capture start date on the report so an empty range for the new
   fields is not misread as "nothing changed".

## Consequences

- Historic manager/department/designation changes are unrecoverable — nothing
  was written. Capture begins 31 Jul 2026.
- One extra audit row per changed field per profile update (bulk imports that
  touch many fields will write proportionally more rows); acceptable for an
  audit surface and bounded by existing retention policy.
- Rollback: re-point the trigger at the legacy function. Additive; no data loss.

Guard: `src/test/reports/changeHistory.test.ts`.
