# ADR-047: Multi-Month KPI Score Percolation

## Status
**Accepted**

## Date
2026-04-01

## Context
When a multi-month KPI is approved at its terminal month, sibling months in the same cycle need to reflect the same scores and approved status.

## Decision
The `percolate_multimonth_score` database trigger fires when a terminal-month KPI transitions to `approved`. It propagates all score fields, ratings, achieved_value, and is_na to sibling KPIs. Siblings already approved are skipped. Status is set to `approved` BEFORE the submission upsert to prevent trigger conflicts.

## Alternatives Considered

### Alternative A: Manual per-month approval
- **Description:** Require reviewers to approve each month in the cycle individually
- **Rejected because:** Multi-month KPIs represent a single measurement across the cycle. Requiring separate approvals for identical data is redundant and error-prone.

### Alternative B: Application-level propagation
- **Description:** Handle score propagation in frontend code after approval
- **Rejected because:** Unreliable — browser crashes, network failures, or direct API usage could leave siblings in inconsistent state. DB triggers guarantee atomic propagation.

## Consequences

### Positive
- Atomic, guaranteed score propagation
- Consistent data across all months in the cycle

### Negative
- Trigger ordering matters (status before submission to avoid lock trigger conflicts)

### Neutral
- Audit trail via `SCORE_PERCOLATED` action in `kpi_audit_logs`
