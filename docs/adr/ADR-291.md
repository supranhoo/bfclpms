# ADR-291 — Group definition edit: apply to current and future months

Status: Accepted · 2026-08

## Context
`GroupDefinitionEditDialog` could only edit the KPI definition for the single
period selected in the Performance Console scope. Changing a target, weightage
or cycle "from now on" forced the admin to repeat the same edit month by month,
which is slow and drifts (a missed month leaves an inconsistent definition).

## Decision
Add an **Apply to** control to the group definition edit:

- `This month only` (default, unchanged behaviour)
- `This and all future months` — selected month → June of the same fiscal year
- `Next N months` — 2..12 inclusive of the selected month

The span is resolved client-side by `src/components/admin/bu-console/groupEditSpan.ts`
on top of `src/lib/rolloverTargets.ts` (fiscal cycle July–June), then the existing
`bu_console_group_edit_definition` RPC is invoked once per month, sequentially.

Invariants:
- Past months are never written. If the selected period is already in the past,
  only `This month only` is offered.
- Hard cap of 12 periods per run (`MAX_ROLLOUT_PERIODS`).
- Dry-run runs for every target month; the dialog shows a per-month table plus
  a grand total. Months with no matching rows are labelled "no matching rows".
- Commit stops at the first failing month and reports which months were written.
- Each month writes its own `bu_console_edit_runs` row, so undo stays per-month
  and the audit trail is unchanged.
- Weightage impact, cycle clashes and skip lists continue to describe the
  selected month (the anchor of the span).

## Consequences
No schema or RPC change. Rollback = revert the UI/orchestration; the underlying
single-period RPC is untouched.

Tests: `src/test/groupEditSpan.test.ts` (span resolution incl. year wrap, past
month guard, 12-period cap, aggregation with failures).
