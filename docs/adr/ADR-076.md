# ADR-076 — Canonical KRA/KPI text in `org_kpi_data_owners`

Status: Accepted (2026-06-06)

## Context

`OrgKpiOwnerDialog`, the `useIsOrgKpiDataOwner` access gate, and the
`Data Owner: …` badges all read `org_kpi_data_owners` with exact
`.eq()` matches on `(category_id, kra_name, kpi_name)`. A DB scan found
228 of 233 owner rows did not match any row in the `kpis` master:
legacy insert paths had collapsed newlines (`\n`, `\r\n`) in
`kra_name`/`kpi_name` to `" - "`. Same length, different bytes →
`.eq()` never matched, so assigned data owners appeared as
*No data owners assigned* and the access gate denied edit access.

## Decision

1. Repair existing rows (migration `repair_org_kpi_owner_canonical_keys`):
   - Snapshot `org_kpi_data_owners` into
     `org_kpi_owner_key_backup_2026_06` (admin-readable).
   - Delete non-canonical duplicates whose canonical equivalent already
     exists for the same `(category_id, owner_id)`.
   - Update remaining mismatched rows so `kra_name` / `kpi_name` match
     the `kpis` master byte-for-byte, using whitespace-normalized
     equality.
2. Canonicalize on insert in `useAssignOrgKpiOwner`: look up the
   canonical `(kra_name, kpi_name)` in `kpis` via whitespace-normalized
   equality before inserting. Fall back to the supplied text if no
   master row matches.
3. Leave the read hooks unchanged — they continue to use `.eq()`,
   which is correct once storage is canonical.

## Consequences

- Owner dialog and `Data Owner: …` badges immediately reflect the real
  assignments.
- 3 truly orphan owner rows remain (KPIs no longer in master); they
  are kept for admin review, not deleted.
- Rollback: restore from `org_kpi_owner_key_backup_2026_06` via
  `UPDATE org_kpi_data_owners o SET kra_name = b.kra_name, kpi_name =
  b.kpi_name FROM org_kpi_owner_key_backup_2026_06 b WHERE o.id = b.id`.
