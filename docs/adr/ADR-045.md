# ADR-045: Frequency-Aware KRA Rollover

## Status
**Accepted** — Amended 2026-04-05

## Date
2026-04-01

## Context
Multi-month KPIs (Quarterly, Bi-Monthly, etc.) need special handling during rollover. The rollover must create records for the correct months and handle frequency lock triggers.

## Decision
Rollover resolves target `review_period` to the cycle's terminal month. For multi-month KPIs, records are created for ALL months in the cycle >= the target month. Dedup uses `kra_name + kpi_name + review_period` per-month (not terminal-only). Service role callers bypass frequency lock triggers.

### Amendment: Cycle Completion Gate (2026-04-05)

The `enforce_frequency_lock_on_submission` trigger has been enhanced with two additional guards:

1. **All-transition sibling block:** Sibling (non-terminal) months are blocked from ALL status transitions, not just `kra_set → self_review`. This prevents KPIs that bypassed the initial check from progressing through the workflow.

2. **Date-based cycle completion check:** Terminal months are blocked from entering the review workflow (`kra_set → self_review`) until `CURRENT_DATE > last day of terminal month`. For example, a Q1 March KPI can only be reviewed starting April 1.

UI enforces the same via `isCycleComplete()` in `frequencyUtils.ts`.

## Alternatives Considered

### Alternative A: Create only terminal month record
- **Description:** Rollover creates a single record at the terminal month only
- **Rejected because:** Sibling months would not appear in scorecards, would be excluded from weightage calculations, and would not receive percolated scores.

### Alternative B: KRA-level terminal dedup
- **Description:** Check dedup only at the terminal month for the entire KRA
- **Rejected because:** Would block sibling month creation when the terminal month already exists from a prior rollover.

### Alternative C: UI-only cycle gate (no trigger enhancement)
- **Description:** Only add the cycle completion check in the frontend
- **Rejected because:** Would not prevent API-level or migration-level premature reviews.

## Consequences

### Positive
- Complete cycle visibility in scorecards
- Sibling months participate in weightage calculations
- Score percolation works correctly
- No premature reviews possible (enforced at DB + UI level)

### Negative
- More records created per rollover (acceptable for data completeness)

### Neutral
- Non-terminal months locked by `enforce_frequency_lock_on_submission` trigger
- Terminal months gated by cycle end date
