# ADR-225: Admin score corrections (downgrades) in Annual Review bulk data upload

- Status: Accepted (August 2026)
- Context: A cycle-wide upload of corrected production / preventive-maintenance actuals produced `0 apply / 267 skip`, because ADR-171 blocks any cell whose new score is lower than the stored score on completed rows, and `admin_apply_system_scores_upgrade` enforces the same monotonic rule in the database. The corrected figures are genuinely lower, so upgrade-only was the wrong policy for a correction run.
- Decision:
  - Add an admin opt-in **"Allow downgrades (corrections)"** in the Bulk Data Upload dialog, available only when "Apply to Completed reviews" or "Apply to mid-workflow reviews" is on. It requires a free-text correction reason of at least 10 characters.
  - The dry-run then renders a lower score as a normal change flagged `direction: 'down'` (red, with the previous points) instead of skipping it, and the header shows an `N downgrades` badge. With the flag off, behaviour is byte-identical to ADR-171/ADR-186.
  - New SECURITY DEFINER RPC `admin_apply_system_scores_correction(p_instance_id, p_system_scores, p_system_scores_raw, p_reason, p_total_score, p_final_rating)` — admin/hr_pms only, requires a reason, merges cells in either direction, writes `system_scores.admin_correction` to `annual_review_access_audit` with the complete before/after maps, and never touches `overall_status`. `admin_apply_system_scores_upgrade` is left untouched.
  - `commitDryRun` routes a row to the correction RPC only when the row contains at least one downward cell; every other row still goes through the upgrade RPC or the direct safe-stage write.
- Consequences: completed reviews are correctable downward by admins, with mandatory justification and reversible audit rows. Bell-curve, slab and calibration outputs shift after such a run — the dry-run downgrade badge makes that visible before commit.
