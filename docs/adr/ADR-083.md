# ADR-083 — Dashboard aggregate RPCs

Date: 2026-06-09
Status: Accepted

## Context
`AdminDashboard` and `ManagementDashboard` were pulling raw rowsets (14 k+ `kpis`, 2.5 k `profiles`, full `kpi_queries`) and aggregating in JS on every focus. PostgREST one-to-many embeds re-evaluated RLS per row; `pg_stat_user_indexes` showed `idx_kpis_org_period_status` averaging 4,343 tuples/scan. AdminDashboard refetched 5 queries every focus with no `staleTime`.

## Decision
Add two read-only `SECURITY DEFINER` aggregate RPCs (mirrors the proven `get_reviewer_*` pattern):

- `get_admin_dashboard_stats() → jsonb` — one row containing employee count, open queries, pending rollbacks, locked/active period counts, and `stage_counts` from `public.kpis`.
- `get_management_dashboard_rows(p_year, p_months text[], p_employee_ids uuid[])` — server-side `kpis ⨝ review_submissions` join returning only the columns the existing JS aggregator reads.

The Management dashboard keeps `getKpiDueDate` (TS) as the source of truth for overdue logic; the RPC only replaces fetching, not aggregation. This eliminates parity risk.

Cache tuning: `staleTime` 60 s on dashboard queries, 2–5 min on roster/filter hooks (`useProfiles`, `useTeamMembers`, `useSkipLevelTeamMembers`, `useProfilesByWorkflowStage`, `useEmployeeFilterOptions`, `useRollbackStatusCounts`, `usePendingAdjustmentCount`).

## Consequences
- AdminDashboard: 5 queries → 1; full `kpis.status` scan eliminated.
- ManagementDashboard: PostgREST embed + N×1000 `.range()` loops → 1 RPC per calendar year; per-row RLS removed.
- Read-mostly caches survive panel switches and focus events.
- Rollback: drop the RPCs and revert the two callers; `useQuery` cache options can be lowered without functional impact.

## Out of scope (Step 5 follow-up)
Consolidating `useProfilesByWorkflowStage` round-trips (roster + workflow bulk + KPI seed + score-signature seed) into one RPC. Tracked separately to keep this change reviewable.
