# ADR-301 — Central Data Approval → Score Propagation (Step 1: schema + RPCs)

- **Status:** Accepted (server layer only; no UI yet)
- **Date:** 18 August 2026
- **Related:** ADR-259..ADR-297 (Performance Console), POLICY §88 (submission snapshot
  immutability), POLICY §CONSOLE-CENTRAL-APPROVAL-SSOT

## Context
Families of KPIs (Production, Maintenance, Budget vs Actual, Manning norm, Training,
Safety) are one organisational number that many employees are scored on. `org_kpi_values`
already stores that number per scope/period with bands, evidence and remarks, and
propagation into employee rows already exists — but the central record had **one**
approval hop and approving it did not close the employees' review stages.

## Decision
Give the central record its own configurable approval ladder, and make final approval the
event that derives every mapped employee's score.

- `org_kpi_central_registry` — which KPI definitions are central, their
  `propagation_mode` (`central_fed` default | `central_approved`) and optional cut-off day.
- `org_kpi_approval_chains` — ordered steps per definition, `effective_from`-dated, each
  step naming a person (`approver_id`) or a role (`approver_role`).
- `org_kpi_approvals` — immutable one-row-per-decision trail (`submitted`, `approved`,
  `sent_back`, `finalised`, `auto_closed`). No UPDATE/DELETE policy exists.
- `org_kpi_values` gains `workflow_stage`, `current_step`, `submitted_at`,
  `propagation_mode` (all additive, all nullable).
- RPCs (SECURITY DEFINER, dry-run first, no client writes): `org_kpi_chain_upsert`,
  `org_kpi_chain_list`, `org_kpi_submit_value`, `org_kpi_decide`, `org_kpi_finalise`.

### Locked semantics
1. **Same value, per-employee bands.** `org_kpi_finalise` copies the approved achieved
   value and recomputes each employee's 0–5 score with
   `fn_compute_rating_from_achievement(kpis, value)` against *their* target/R5–R0 row.
2. **Frozen snapshot.** The value is written into `review_submissions`, never linked
   (POLICY §88). Rows with `final_score IS NOT NULL` are skipped as `final_score_locked`.
3. **Mode decides stage closure.** `central_fed` writes the value and lets the normal
   review run (`kra_set` → `self_review` only). `central_approved` additionally fills the
   employee's remaining resolved stages **when empty** and moves `kpis.status` to the last
   non-`approved` stage of `get_employee_workflow` — never a hardcoded ladder.
4. **Send-back returns to the data provider**, with the rejecting step recorded.
5. Skips are reported by reason (`no_submission`, `final_score_locked`, `not_scoreable`),
   never fatal to the run.

## Consequences
- Positive: one entry point per organisational number, an auditable ladder, and provider
  timeliness derivable from `org_kpi_approvals` with no new capture.
- Negative: a second place a workflow can live (central chain vs per-employee workflow);
  they are deliberately independent and only meet at finalisation.
- Nothing changes for any KPI until an admin registers it — the registry is empty on ship.

## Rollback
Drop the three tables, the four added `org_kpi_values` columns and the nine functions.
Existing propagation, scoring and workflows are untouched by design.
