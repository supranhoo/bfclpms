# ADR-241 — Inactive employee suppression

**Status:** Accepted — 2026-08-03
**Policy:** POLICY §SEC-INACTIVE-SUPPRESSION

## Context

`profiles.is_active = false` marks an employee who has left or been deactivated. The flag
was honoured in dashboards and reports, but not in two delivery paths:

- The `notifications` INSERT policy checked only `can_send_notification_to(...)`, which
  contains no activity test. Worse, nearly all producers are SECURITY DEFINER triggers
  that bypass RLS entirely — only the KPI-auditor trigger filtered `is_active`.
- `resetPasswordForEmail` was called directly from the sign-in screen, and the admin
  `reset-password` edge function selected only `id` from `profiles`.

Result: deactivated staff kept receiving in-app notifications and email, and could still
recover access to the system.

## Decision

Enforce suppression at the narrowest chokepoint of each path.

1. A BEFORE INSERT trigger on `public.notifications` silently drops rows for inactive
   recipients. Silent (return NULL) rather than raising, because notification inserts sit
   inside business transactions — the ADR-037/§108 precedent.
2. The RLS `WITH CHECK` also calls the helper, so client inserts fail loudly instead of
   disappearing.
3. Outbound email is gated once inside `send-email-notification`; every scheduler routes
   through it.
4. Password reset is gated by `password_reset_allowed`, reusing the
   `auth_lookup_attempts` throttle and the anti-enumeration UI contract already used by
   employee-code login.

## Consequences

- Work assigned to an inactive reviewer produces no pings. Reviewer reassignment remains
  the remedy; this is intended, not a regression.
- Rollback is dropping the trigger and reverting the policy; no data migration.
