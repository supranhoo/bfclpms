# ADR-032: Review Journey Previous Month Comparison

## Status
**Accepted**

## Date
2026-03-30

## Context
Reviewers need to compare current KPI performance against recent history without switching dashboards. The previous month data display needed a data-sourcing strategy.

## Decision
The Review Journey shows up to 2 previous months using live database queries (same `kpis` + `review_submissions` tables), with staleTime ≤ 2 minutes. Each previous month's workflow is resolved independently via `get_bulk_employee_workflows` RPC. KPIs matched by `employee_id + kpi_name + kra_name + category_id`.

## Alternatives Considered

### Alternative A: Snapshot/cached previous month data
- **Description:** Store a frozen snapshot of previous months' scores at period close
- **Rejected because:** Stale snapshots would not reflect corrections, rollbacks, or late entries made after period close. Live data ensures reviewers always see the current truth.

### Alternative B: Match previous KPIs by KPI ID
- **Description:** Use the KPI's UUID to find prior months
- **Rejected because:** KPI IDs are unique per period — each month generates new KPI records. Matching must use the composite key (employee + KPI name + KRA name + category).

## Consequences

### Positive
- Reviewers see real-time accurate historical data
- Corrections to past periods are immediately reflected

### Negative
- Additional database queries per review (mitigated by staleTime caching)

### Neutral
- Workflow resolution per month adds complexity but ensures correct stage display
