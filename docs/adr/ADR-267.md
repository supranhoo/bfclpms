# ADR-267 — Goals rebuilt as Category → KRA → Goal → Sub-goal

- **Status:** Accepted
- **Date:** 16 August 2026
- **Related:** ADR-263, ADR-264, ADR-265, POLICY §BU-CONSOLE-GOAL-HIERARCHY

## Context
ADR-263 modelled a goal as one row per `kpi_definitions_master` definition.
`kpi_definitions_master` is empty (0 rows) while live review data holds 17,594
`kpis` rows for 2026 across 81 categories and 440 KRAs, so no goal could ever
attach to real data. Users also expect goals to live *inside* the category /
KRA tree they already navigate (e.g. Production → CPP → "45 MW AFBC"), not in a
flat list between the console and the KPI library.

## Decision
A goal is a **named target anchored to a KRA category**, optionally narrowed to
a KRA and a KPI name, with one level of sub-goals.

- `bu_goals` gains `title`, `category_id`, `kra_name`, `kpi_name_match`,
  `weight`, `goal_source`; `definition_id` becomes nullable.
- `goal_source` is explicit: `kpi_rollup` (weighted aggregation of matching
  live `kpis` rows), `child_rollup` (weight-weighted sum of sub-goals), or
  `manual`.
- Nesting is capped at one level (goal → sub-goal) — enforced server-side.
- `bu_goal_kra_options` supplies KRA/KPI pickers from live review data with a
  bounded, searchable list (ADR-264: totals are always reported).

## Consequences
- **Positive:** goals attach to data that exists; the hierarchy matches how the
  business talks about targets; roll-up stays weighted and explainable.
- **Negative:** name-based matching (category + KRA + KPI text) is looser than
  an ID link; the standardization registry remains the long-term fix.
- Employee scoring, workflows and review data are untouched by design.

## Rollback
Drop the added columns and revert the three RPCs to their ADR-263 bodies.
