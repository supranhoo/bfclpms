# ADR-092 — Org KPI submission fallback coalesces over snapshot columns

- **Date:** 2026-06-28
- **Status:** Accepted
- **Related:** ADR-055 (fact-based status), ADR-063 (per-row OKV pill), ADR-091 (Bulk Rollback OKV-truth gate), POLICY §88 (Submission Snapshot Immutability)

## Context

Reported by Biswajit Sahoo (2026-06-28): on `/admin/org-kpi-data` the KPI *"Achieve organization's production target → Handle all breakdowns…"* for May 2026 / Y R V S Murthy showed `—` in the Achieved column, while the KPI Details modal for the same employee showed *Self 9.67 · Manager 9.67 · Rating 2*. The two surfaces disagreed.

Forensic trace (from `org_kpi_data_entry_logs` + `review_submissions`):

1. 2026-06-10 — Biswajit propagated 15.16 while children were at `kra_set`.
2. 2026-06-15 — Admin bulk zero-score advanced children past `kra_set`.
3. 2026-06-17 — Employee self-submitted → `self_achieved_value = 9.67`; manager later set `manager_achieved_value = 9.67`, `manager_score = 2`.
4. 2026-06-23 — Admin executed three `rollback_to_data_entry` actions per Biswajit's request → OKV achieved values cleared. Per POLICY §88, child `review_submissions` snapshots were NOT touched.
5. 2026-06-28 — Biswajit re-entered 9.67 / 10 / 15.16 and propagated. The RPC honoured POLICY §88 and did NOT overwrite the already-frozen `self_achieved_value` / `manager_achieved_value` columns.

The hook `useOrgKpiSubmissionFallback` only read `review_submissions.achieved_value` (the data-owner column). That column was `NULL` for every advanced child, so the fallback returned no value and the row collapsed to `—` — even though the real value (the frozen snapshot) was visible to the employee on their own scorecard.

## Decision

`useOrgKpiSubmissionFallback` now coalesces the resolved value across three `review_submissions` columns in priority order:

```
achieved_value           (data-owner)
  ?? manager_achieved_value
  ?? self_achieved_value
```

Each fallback entry now carries a `valueSource: 'owner' | 'manager' | 'self' | 'none'` field so the UI can disambiguate "OKV truth" from "frozen reviewer snapshot" when the badge is wired in a follow-up.

The change is strictly **read-only display**. POLICY §88 (Submission Snapshot Immutability) is unchanged — propagation still refuses to overwrite frozen columns, and no new write paths are introduced. The OKV row's own `achieved_value` continues to win whenever it is non-NULL (existing rule in `OrgKpiDataEntry.tsx::buildCardData`, preserved).

## Consequences

- Y R V S Murthy / May 2026 now renders `9.67` in the OKV row, matching the KPI Details modal.
- Admins gain visibility into "where did the displayed value come from?" via `valueSource`. The visible badge wiring is staged as a follow-up PR — this ADR ships the data layer only.
- The hook still uses `staleTime: 30s`; no new round trips. The added columns are tiny scalars on rows we were already fetching.

## Deferred follow-ups (tracked in CAPA plan)

1. UI source-of-truth badge on `ScopedRow` ("from snapshot" hint) when `valueSource !== 'owner'`.
2. Pre-rollback confirm dialog enrichment that lists children already past `kra_set` and warns that re-propagation will be a no-op against their snapshots.
3. Admin-only `resync_org_kpi_snapshot(scope_id, period, year, reason)` RPC with mandatory `OKV_FORCED_RESYNC` audit row, used to deliberately overwrite a non-`kra_set` snapshot. Final-score-approved children remain immutable.
4. Generalise the coalescing pattern into a shared helper for the Daily KPI and Safety surfaces that read similar snapshot columns.

## Tests

- `src/test/orgKpiSnapshotFallbackCoalesce.test.ts` — 6 cases pinning the owner → manager → self priority, NULL-everywhere behaviour, NA semantics, and the exact Y R V S Murthy regression scenario.
- Existing `src/test/orgKpiPostPropagationHydration.test.ts` continues to pass — owner-value-wins precedence is unchanged.

## Rollback

Revert `src/hooks/useOrgKpiSubmissionFallback.ts` and delete the new test file. No schema, RLS, RPC, or data change.
