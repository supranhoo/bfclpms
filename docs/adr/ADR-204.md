# ADR-204 — Backup transient resilience: upload retry, widened backoff, reconciliation sweep

## Status

Accepted — 2026-07-30.

## Context

Two scheduled backups failed inside five days, both from recoverable
upstream transients rather than capacity limits:

| Run | Status | Coverage | `backup_logs.error_message` |
|---|---|---|---|
| 2026-07-26 17:00 | failed | 238/239 | `Skipping table annual_review_reviewer_resync_audit: Upload …part-000001.json failed: Gateway Timeout` |
| 2026-07-29 17:00 | failed | 247/248 | `Batch 2/62 … transient: HTTP 502; sub 2/4 [annual_review_bu_removal_repair_2026_07] failed after 2 retries: HTTP 502 (budget 427s left)` |

`annual_review_bu_removal_repair_2026_07` holds 34 rows / 64 kB, so neither
failure was memory- or size-related (ADR-082 already bounds per-table heap).

Three gaps in the recovery envelope:

1. **No upload-level retry.** `streamTableToStorage` threw on the first
   `upload()` error. `processTableBatch` catches it into `errors` and
   `handleBatch` still answers HTTP 200, so the batch retry layer never
   even sees the failure — the table is simply gone from the manifest.
2. **Backoff too short.** `RETRY_BACKOFFS_MS = [5s, 15s]` gives 3 attempts
   inside ~20 s. Gateway 502 windows routinely outlast that, and the run
   ended with 427 s of `RETRY_BUDGET_MS` unspent.
3. **No reconciliation pass.** Once a batch's retries were exhausted
   mid-run, the missing table was never re-attempted before finalize,
   even with minutes of budget left.

The coverage guard and `backup_hard_fail_on_partial` then behaved
correctly — the policy was right, the upstream resilience was not.

## Decision

1. `uploadPartWithRetry` wraps every part-file upload:
   `UPLOAD_RETRY_BACKOFFS_MS = [1s, 3s, 8s]`, transient-only
   (`Gateway Timeout` / timeout / `isTransientChunkError`), `upsert: false`
   on attempt 1 and `upsert: true` on retries so a half-written object is
   replaced rather than colliding.
2. `RETRY_BACKOFFS_MS` widened to `[5s, 15s, 45s, 90s]` — 4 attempts across
   ~2.6 min, well inside the unchanged 8-min `RETRY_BUDGET_MS`.
3. `runScheduledChunked` performs a coverage reconciliation sweep before
   `finalize`: diff `tableManifest` against the discovered table list and
   re-invoke the worker once per missing table while budget remains.
   Outcomes are appended to `errors` under a `reconcile:` prefix.
4. Hard-fail-on-partial is untouched and remains terminal.

Unchanged Phase-9 invariants: `BATCH_SIZE = 4`, `BATCH_SIZE_RETRY = 1`,
`RETRY_BUDGET_MS = 8 * 60_000`, `ROWS_PER_CHUNK = 5000`, `PAGE_SIZE = 1000`,
`loadHardFailOnPartial`, and the no-download-in-`verifyBackupIntegrity`
contract (ADR-082 / WP-9.2.d).

## Consequences

- Worst-case scheduled-run wall time grows by up to ~2-3 min, and only when
  transients actually occur; nominal runs (~3-4 min) are unchanged.
- Retried uploads may overwrite an object written by a lost attempt. This is
  safe: part content is deterministic for a given table page range within a
  run, and the target folder is unique per backup.
- `backup_logs.error_message` may now carry a `reconcile:` segment even on
  runs that ultimately complete — that is intended telemetry.
- No DB migration, no RLS change, no manifest-format change; `restore-backup`
  and `useDownloadBackup` are untouched.

## Rollback

Revert `supabase/functions/create-backup/index.ts` and delete
`src/test/infra/backupTransientResilienceContract.test.ts`. Artifacts
produced under ADR-204 remain restorable either way because the storage
layout is unchanged.
