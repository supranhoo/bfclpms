# ADR-096 — Admin / HR PMS on-behalf writes to `review-evidence`

Date: 2026-06-29
Status: Accepted

## Context

Admin 101785, doing Admin Data Entry on behalf of Sajid Raza (100264) for the
May 2026 Org KPI "Enhance Campaign Life", clicked **Add files** in the
Evidence Attachments picker and got:

> Upload failed — new row violates row-level security policy

`src/components/ui/EvidenceUpload.tsx` builds the storage path as
`${userId}/${kpiId}/<timestamp>_<file>`, where `userId` is the employee
being acted upon, not the signed-in admin. That is correct: the employee
and their reporting chain need to be able to read the file via the existing
`Users can view authorized evidence` SELECT policy, which keys off
`storage.foldername(name)[1] = employee.id`.

But the `review-evidence` bucket only had two INSERT policies:

1. `Users can upload their own evidence files` — `auth.uid()::text = foldername(name)[1]` (fails for on-behalf paths).
2. `Org KPI evidence insert` — restricted to the `org-kpi-evidence/` prefix.

There was no admin / HR-PMS write policy for the per-employee folder layout,
so every on-behalf upload was rejected. View (SELECT) worked because the
SELECT policy already grants admin/auditor/hr_pms/manager/skip-level read.
The write side was the asymmetry.

Scope: affects every admin/HR-PMS on-behalf evidence upload through
`EvidenceUpload` (Admin Data Entry, Annual Review proxy, anywhere this
component is mounted), not just KPI 101785.

## Decision

Add three additive permissive policies on `storage.objects` scoped to
`bucket_id = 'review-evidence'` and gated by
`has_role(auth.uid(), 'admin') OR has_role(auth.uid(), 'hr_pms')`:

- `Admins and HR PMS can upload evidence on behalf` (INSERT, WITH CHECK)
- `Admins and HR PMS can update evidence on behalf` (UPDATE, USING + WITH CHECK)
- `Admins and HR PMS can delete evidence on behalf` (DELETE, USING)

The existing per-user, Org-KPI, and authorized-read policies are left in
place. Auditors stay read-only by design — they observe evidence, they
don't add it.

No application-code change. `EvidenceUpload.tsx` already writes to the
correct (employee) folder, which is what we want so the employee and their
reporting chain can read what the admin uploaded.

## Alternatives considered

1. Use `admin.uid()` as the first folder segment — rejected, breaks the
   existing SELECT policy that keys read access on the employee folder.
2. Route uploads through an edge function with `service_role` — rejected,
   heavier change with no benefit once RLS reflects the privilege model.

## Consequences

- Admin and HR PMS can now upload, replace, and delete evidence on any
  employee's `review-evidence` folder. Mirrors the read side.
- No privilege change for `employee`, `manager`, `skip_level`, `auditor`,
  `management`.
- Audit trail unchanged — uploads from Admin Data Entry still ride the
  `kpi_audit_logs` write path with `performed_by = admin`,
  `on_behalf_of = employee_id`.

## Rollback

```sql
DROP POLICY IF EXISTS "Admins and HR PMS can upload evidence on behalf" ON storage.objects;
DROP POLICY IF EXISTS "Admins and HR PMS can update evidence on behalf" ON storage.objects;
DROP POLICY IF EXISTS "Admins and HR PMS can delete evidence on behalf" ON storage.objects;
```

`src/test/reviewEvidenceOnBehalfPolicy.test.ts` — source-reading regression

correct bucket + role guards (same pattern as ADR-095).
