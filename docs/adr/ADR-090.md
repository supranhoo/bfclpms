# ADR-090 — Multi-month cycle anchor drift: backfill repair + intra-year consistency guard

**Date:** 2026-06-28
**Status:** Accepted
**Related:** ADR-087, ADR-088

## Context

Sajid Raza's Bi-Monthly KPIs (anchor `Feb-Mar` → cycles Feb-Mar / Apr-May /
Jun-Jul / …) showed the correct anchor on April 2026 but had drifted to
`May-Jun` on May 2026 and June 2026 — the same defect ADR-088 fixed
forward for Prabhat Kumar Singh. A full-system scan found **42 tuples**
(41 Bi-Monthly + 1 Half-Yearly) with intra-year anchor divergence: rows
created by the pre-ADR-088 cron rollover (April–June 2026) had their
`frequency_cycle_start` silently rewritten to the Jan-anchored standard
window, while April 2026 rows authored before the bug kept the original
offset anchor.

ADR-088 fixed `auto-rollover-kpis::buildNewKpi` and the
`resolve_cycle_anchor(_, _, _)` 3-arg sticky overload but only repaired
the two rows that triggered the original report. Pre-existing drift on
other tuples was never back-corrected, and no daily detector was wired
to alert when drift reappeared.

## Decision

1. **Backfill repair (one-shot).** New admin-only SECURITY DEFINER RPC
   `public.repair_intra_year_cycle_anchor_drift(p_dry_run, p_safety_ceiling)`
   implements an *oldest-row-wins* strategy: for each
   `(employee_id, kpi_name, review_year)` tuple, the row with the earliest
   `created_at` carries the authoritative anchor (it pre-dates any buggy
   rollover). All later siblings whose anchor differs are corrected to
   match, provided the authoritative anchor passes
   `is_valid_cycle_anchor(frequency, anchor)`. Every UPDATE writes a
   `kpi_audit_logs` row with `action='KPI_CYCLE_ANCHOR_REPAIRED'` and
   `metadata.policy='ADR-090'`, `metadata.strategy='oldest_row_wins'`.
   A safety ceiling aborts the run if planned updates exceed 500 rows.
   No score, submission, or status field is touched — POLICY §88
   immutability is preserved.

2. **Detector RPC.** New `public.detect_intra_year_cycle_anchor_drift()`
   returns one row per drifted tuple with the list of conflicting anchors.
   Cheap (single GROUP BY HAVING) and safe to call daily.

3. **Prevention trigger.** New `BEFORE INSERT` trigger
   `trg_enforce_intra_year_cycle_anchor_consistency` on `public.kpis`
   rejects any new row whose `frequency_cycle_start` conflicts with an
   existing row for the same employee + KPI + year + frequency. UPDATEs
   are exempt (intentional — the repair tool and admin propagation paths
   need to converge anchors). Error message names the existing anchor so
   the offending caller can self-correct.

## Consequences

- 89 KPI rows across 42 tuples were repaired in the same migration
  window; `detect_intra_year_cycle_anchor_drift()` now returns 0 rows.
- Future cron rollovers cannot reintroduce the bug at the row level —
  the trigger blocks the insert before it hits the table. Combined with
  ADR-088's sticky `buildNewKpi`, the failure mode is closed by two
  independent controls.
- ADR-087 client-side rendering (`buildCycleScopeLabel`) immediately
  shows the corrected anchor — no UI change required for affected
  employees.
- The repair is fully reversible: each change is captured in
  `kpi_audit_logs` with both `old_value` and `new_value`.

## Files

- `src/lib/cycleAnchorRepair.ts` + `src/test/cycleAnchorRepairSelection.test.ts`

  + operational contract.

## Follow-ups (not in this ADR)

- Daily `cycle-anchor-drift-monitor` edge function + cron + admin
  banner. Tracked separately; the prevention trigger already closes the
  recurrence risk so the monitor is observability, not a guardrail.
- Soft-deprecate the 2-arg `resolve_cycle_anchor(frequency, month_idx)`
  in favour of the 3-arg sticky overload (after auditing external
  callers).
