# ADR-068: Confirmation Increment — Company Scope & Transition Gating

**Status:** Accepted · 2026-05-31

## Context
The Confirmation Increment Adjustment rule applied uniformly to every
confirmation event. This risked suppressing annual increments for lateral
hires whose probation-to-confirmation transition does not include a
confirmation salary revision.

## Decision
1. **Transition gating.** `confirmation_increment_rules.applicable_transitions text[]`
   (default `{trainee_to_confirmed}`) restricts the adjustment to selected
   pre→post status transitions. The pure adjuster
   (`src/lib/confirmationIncrementAdjuster.ts`) short-circuits to `ignore` when
   the employee's `previous_employment_status` does not map to an entry in the
   list. Backward-compatible: legacy callers that omit the list keep the
   pre-existing (ungated) behaviour.
2. **Company scope.** Three modes via `company_scope_mode`:
   - `global` — single rule for all companies (existing behaviour, default).
   - `selected` — same rule limited to `selected_company_ids uuid[]`.
   - `per_company` — distinct rule row per `company_id`.
3. **Previous status capture.** `profiles.previous_employment_status text NULL`
   stores the pre-confirmation status. Engine treats unknown/null as
   ineligible (safe default — never penalise without evidence).
4. **Canonical mapping** lives in code (`statusToTransition`) and is
   case-insensitive. Adding a new transition requires updating the union type,
   `TRANSITION_LABELS`, and the mapper — no hardcoded UI strings.

## Consequences
- Lateral/probation hires are protected by default — `applicable_transitions`
  must explicitly include `probation_to_confirmed` for the rule to bite.
- Per-company HR policies can now diverge without forking the engine.
- Adjuster remains a pure function — no DB coupling, easy to unit-test.

## Rollback
Drop the three new columns on `confirmation_increment_rules` and the
`previous_employment_status` column on `profiles`. UI gracefully degrades.
