# ADR-034: Admin Edit Final Score Recomputation

## Status
**Accepted**

## Date
2026-03-30

## Context
When an admin edits score fields on an already-approved KPI, the `final_score` needs to stay consistent. The normal approval flow sets `final_score` during status advancement, but approved KPIs skip that flow.

## Decision
Post-upsert recomputation of `final_score` must always execute when `currentKpiStatus === 'approved'`, using the 8-stage fallback chain (management → auditor → HR PMS → skip-level → manager → self). This is independent of the `advance_status` toggle.

## Alternatives Considered

### Alternative A: Gate recomputation behind the `advance_status` toggle
- **Description:** Only recompute final_score when `advance_status` is enabled
- **Rejected because:** The toggle controls workflow progression, not score integrity. Approved KPIs never advance, so tying recomputation to the toggle would leave `final_score` permanently stale after admin edits.

### Alternative B: Prohibit admin edits on approved KPIs
- **Description:** Lock all score fields once KPI reaches approved status
- **Rejected because:** Admins need to correct data entry errors and handle late adjustments. Blocking edits entirely removes a necessary administrative capability.

## Consequences

### Positive
- `final_score` always reflects the latest admin-entered data
- No manual recalculation needed

### Negative
- Extra computation on every admin edit of approved KPIs (negligible cost)

### Neutral
- Recomputation uses the same 8-stage fallback chain as the approval flow
