# ADR-302 — Performance Console: central KPI value entry and approval rail (Step 2 UI)

**Status:** Accepted · 2026-08-19
**Relates to:** ADR-301 (server layer), POLICY §CONSOLE-CENTRAL-APPROVAL-SSOT

## Context

ADR-301 shipped the server layer for centrally fed organisational KPIs: the
`org_kpi_central_registry`, effective-dated `org_kpi_approval_chains`, the
append-only `org_kpi_approvals` trail, workflow columns on `org_kpi_values`, and
the four `SECURITY DEFINER` RPCs (`org_kpi_chain_upsert`, `org_kpi_submit_value`,
`org_kpi_decide`, `org_kpi_finalise`). Nothing in the product could reach them —
a registered KPI had no surface for a provider to enter a number, no way for an
approver to see it was their turn, and no way for an admin to build a chain.

## Decision

Add the console UI as a thin, additive layer over the existing RPCs. It resolves
nothing on its own: every write is a dry-run preview followed by an apply, and
every gate mirrors (never replaces) the server check.

- **`src/lib/review/centralApprovalModel.ts`** — pure SSOT for the workflow's
  presentation state: `resolveStage` (NULL stage = `draft`), `currentStep`,
  `actorMatchesStep` (named person or role), `canDecide`, `canProvide`,
  `stepStatus` (`done` / `current` / `sent_back` / `pending`), `ageingDays` and
  `stageSummary`. No component derives turn-taking on its own.
- **`src/hooks/useOrgKpiCentralWorkflow.ts`** — React Query wrappers over the
  ADR-301 RPCs plus the registry/chain and trail reads. Mutations take
  `dryRun` so callers can preview before applying.
- **`CentralValuePanel.tsx`** — the "Central data" section on the KPI detail
  modal. Renders only for registered KPIs (admins additionally see a
  "Set up central approval" affordance on unregistered ones). Shows value,
  target, evidence count, stage badge and who holds the row for how long.
- **`CentralApprovalRail.tsx`** — the ordered ladder with each step's holder,
  decision, timestamp and comment. Approve / Send back render only for the actor
  whose step is current; send-back requires a reason.
- **`CentralValueEntryDialog.tsx`** — provider entry for numeric or qualitative
  KPIs, remarks and a shortcut into the shared evidence manager.
- **`CentralChainConfigDialog.tsx`** — admin-only registration and ordered step
  editor with propagation mode, cut-off day and `effective_from`.

Propagation (`org_kpi_finalise`) stays an explicit admin action with a dry-run
preview reporting applied / skipped counts, so POLICY §88 skips
(`final_score_locked`) are visible rather than silent.

## Consequences

- The registry still ships empty; a KPI behaves exactly as before until someone
  registers it. This is a purely additive surface.
- Because the UI gates are mirrors, a stale client can attempt a write but the
  RPC rejects it — the panel surfaces the server's reason verbatim.
- Evidence reuses `OrgKpiEvidenceManagerSheet` and the existing
  `review-evidence` policies; no new storage path or RLS was introduced.

## Regression cover

- `src/lib/review/centralApprovalModel.test.ts` (18) — stage resolution, turn
  taking for named/role steps, send-back returning to the provider, ageing.
- `src/components/admin/bu-console/centralApprovalRail.test.tsx` (3) — actions
  visible only to the current holder; skeleton while loading.
