# ADR-079 — Access-Profile / RLS alignment

Date: 2026-06-06
Status: Accepted

## Context

Access Profiles let admins delegate per-menu CRUD rights (`can_add`,
`can_update`, `can_delete`) to non-admin users. But the underlying tables
(`profiles`, `user_roles`, `access_profile_assignments`, …) have RLS that
only allows admin writes. When a profile-granted user clicked Save:

- Supabase silently filtered the row under RLS,
- `.update()` returned `{ data: null, error: null }`,
- the React Query `onSuccess` toast claimed success,
- **nothing changed in the DB.**

RCA recorded against the User Management → Edit User → Account Status
toggle (Avinash Kumar case, 2026-06-06).

## Decision

Two layers, both required:

### Layer 1 — DB SSOT

1. `public.has_menu_right(_user_id uuid, _menu_key text, _action text)` —
   `SECURITY DEFINER`, `STABLE`, `search_path=public`. Reads
   `access_profile_assignments` → `access_profile_menu_rights` (joined on
   active `access_profiles`) and returns `true` iff the user holds the
   right.
2. Additive permissive RLS policies (existing admin-only policies stay):
   - `profiles` UPDATE — `has_menu_right(auth.uid(), 'admin-users', 'update')`
   - `access_profile_assignments` INSERT — `'admin-access-profiles','add'`
   - `access_profile_assignments` DELETE — `'admin-access-profiles','delete'`
3. **Out of scope (intentionally admin-only):**
   - `user_roles` writes (role changes stay admin-only — privilege escalation
     guard).
   - `access_profile_menu_rights` writes (editing the rights themselves is
     a sensitive admin function).

### Layer 2 — Frontend silent-RLS guard

`src/lib/db/assertRowsTouched.ts` is the canonical helper. Every admin-page
mutation that touches a profile-protected table MUST:

1. append `.select('id')` to the Supabase mutation builder,
2. call `assertRowsTouched(data, error, { menuKey, action, resource })`.

If RLS filters the row (0 rows touched), the helper throws a
`PermissionError` with toast-ready copy. No more silent successes.

### Layer 3 — UI gating (defence in depth)

`useMenuAccess.canPerform(menuKey, action)` is consulted at render time to
disable + tooltip the Save / Assign / Remove buttons when the caller lacks
the right. The DB + toast guard remain the source of truth.

## Consequences

- A non-admin holding `admin-users / update` can now actually save profile
  field edits (name, status, manager, …). They still cannot change roles.
- A non-admin holding `admin-access-profiles / add` (or `/delete`) can now
  actually assign or remove users from profiles.
- Any RLS-filtered write surfaces as a destructive toast, never a fake
  success.
- Rollback: drop the three new policies (`Profile-granted users can …`).
  The `has_menu_right` helper can stay.

## Tests

- `src/test/assertRowsTouched.test.ts` — guard contract (success, RLS
  filter, supabase error, action-verb wording, error metadata).
- `src/test/userManagementSilentRlsGuard.test.ts` — pre-existing,
  documents the BUG-class this ADR closes.

## Out of scope

- Reworking the dual `menu_access_*` vs `access_profile_*` model.
- Extending delegation to other admin menus (KPI, Org KPI, Menu Access).
  Add via the same pattern only after explicit approval.
