# ADR-349 — Org KPI status uses ONE active-employee population

- **Status:** Accepted
- **Date:** 3 September 2026
- **Related:** ADR-055, ADR-064, POLICY §ORG-KPI-ACTIVE-POPULATION

## Context
An Org KPI whose card read "7 of 7 entered / propagated" was still counted under
the **Pending** chip on Organization KPI Data Entry.

`public.get_org_kpi_data_entry_snapshot` applied the `emp_active` filter to the
*mapping* aggregates (`employee_count`, `employee_ids`, `department_ids`) but not
to the *workflow-stage* aggregates (`kra_set_kpi_rows`, `kra_set_emp_ids`,
`propagated_emp_ids`, `per_employee_targets`, `employee_kpi_ids`). An inactive
employee left at `kra_set` therefore could not appear in the numerator but still
made `kraSetEmpIds` non-empty, so `deriveOrgKpiTileStatus` returned `stuck` — and
the Pending chip, computed as `total − entered − propagated`, absorbed it.

23 KPI/period groups in 2026 matched the pattern (e.g. August "Implement 5S
practices": 126 active rows, 0 active `kra_set`, 1 inactive `kra_set`).

## 5 Whys
1. KPI shows Pending → the chip counts everything that is neither entered nor propagated.
2. It is neither → the tile resolved to `stuck`.
3. Stuck → `kraSetEmpIds` was non-empty.
4. Non-empty → it contained an **inactive** employee.
5. Contained → "active employee" was re-expressed inline per aggregate instead of once.

## Decision
1. **Server:** every aggregate in `get_org_kpi_data_entry_snapshot` is now filtered
   by `emp_active`. Signature unchanged (`CREATE OR REPLACE` only).
2. **Client (defence in depth):** `activeKraSetEmpIds()` in `src/lib/orgKpiStatus.ts`
   intersects `kraSetEmpIds` with `mappedEmpIds`; `deriveOrgKpiTileStatus` uses the
   intersected set. `OrgKpiDataEntry` intersects at the source memo so the tile,
   the scoped rows, the Pending Report and the post-propagate accounting all read
   one set.
3. **Chip honesty:** `progressData.pendingKpis` is counted explicitly; `stuck` is
   never re-labelled Pending.
4. **Preview:** `preview_org_kpi_propagation` returns reason `employee_inactive`
   for rows whose employee is inactive; that reason is benign in
   `ALREADY_DONE_REASONS`, in the toast classifier and in the preview dialog labels.

## Consequences
- Affected KPIs move from Pending/Stuck to Propagated — that is the correction.
- No schema change, no row writes, no RLS change; rollback = re-deploy the previous
  function bodies and revert the touched client files.
- Follow-up (not in this change): `propagate_org_kpi_value` and
  `diagnose_org_kpi_propagation_gap` still accept inactive employees as targets
  when ids are supplied directly. They are unreachable from this surface now that
  every client-side id set is active-only, and the preview flags them.

## Diagnostic (read-only)
```sql
select k.review_year, k.review_period, k.kra_name, k.kpi_name,
       count(*) filter (where coalesce(p.is_active,true) and k.status <> 'kra_set') as active_done,
       count(*) filter (where coalesce(p.is_active,true) and k.status = 'kra_set')  as active_kra_set,
       count(*) filter (where p.is_active = false and k.status = 'kra_set')         as inactive_kra_set
from kpis k join profiles p on p.id = k.employee_id
where k.is_org_level
group by 1,2,3,4
having count(*) filter (where coalesce(p.is_active,true) and k.status = 'kra_set') = 0
   and count(*) filter (where p.is_active = false and k.status = 'kra_set') > 0;
```
