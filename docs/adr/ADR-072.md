# ADR-072: Menu/Sidebar CAPA close-out — 3-factor restoration RCA

## Status
**Accepted** (2026-06-04)

## Date
2026-06-04

## Context
On 2026-06-04, admin user `Ankit` landed on `/dashboard` with an empty
sidebar; auditor `Shekhar` hit the page-level `ErrorBoundary`. Root analysis
identified three concurrent failure modes:

1. Live `menu_overrides` rows had re-parented seeded items
   (e.g. `admin-dashboard`, `reports-performance`) under brand-new custom L3
   containers (`custom-dashboards`, `custom-shortcut-*`), hollowing out
   static sidebar groups.
2. The custom synth path in `AppSidebar.synthFromNode` defaulted custom items
   to `roles: ['admin']`, surfacing inconsistencies for non-admins.
3. The deployed bundle (`index-CjfF6RVN.js`) lagged source — fixes in
   `applyOverrides` / `resolveGroupItems` / `useResolvedMenu` were not in the
   running JS.

Restoration was attempted in three concurrent steps. The system became
stable only after **all three** were in place. Single-factor sufficiency was
NOT isolated and will NOT be tested in production.

## Decision
Close the incident as a multi-factor recovery. Capture the four baseline
invariants in code + tests, keep the kill switch held in production, and
block all roadmap re-enablement until a non-prod isolation experiment.

### Restoration factors (all three required for the observed recovery)
1. **Forced republish (r3 3-file diff)** — shipped CAPA code that was in
   source but missing from the previously deployed bundle. The new bundle
   (`index-vo98FbAC.js`) contains:
   - `useResolvedMenu` flag-off short-circuit (`enabled: !!enabled` + a
     hard-guard `if (!enabled) return undefined`).
   - `resolveGroupItems` hard-guard returning the static fallback whenever
     `overridesEnabled === false`.
   - `synthFromNode` defaulting custom items to `ALL_APP_ROLES` so the DB
     `menu_access_config` is the sole visibility gate.
   - `<ErrorBoundary>` wrap around `SidebarContent` with a
     "Menu temporarily simplified" fallback.
   - `applyOverrides` dangling-`parent_key` coercion and `menu_level`
     clamping (1..4).
2. **Flag flip** — `system_settings.menu_overrides_enabled` set to `false`
   at 2026-06-04 07:06:15 UTC.
3. **Override clear** — all active `menu_overrides` rows were deactivated;
   `count(*) where is_active = true` is now 0.

### Why isolation is not claimed
- Stale bundle would defeat **flag-only** recovery: the deployed JS lacked
  the short-circuit, so cached resolver payloads could still render.
- Flag-true + bad overrides would defeat **code-only** recovery: even with
  the new fallbacks, the tree would still try to render a broken override
  graph.
- Cleared rows alone with the old bundle would still miss the
  ErrorBoundary / fail-open paths.
- Verifying single-factor sufficiency requires toggling one lever at a time
  in production. **We are not doing that.** Any future isolation work must
  happen in a non-production copy.

## Baseline invariants (locked by tests)
- **I1** — `system_settings.menu_overrides_enabled = false` ⇒ hardcoded
  baseline sidebar groups render for every authenticated role. No empty
  sidebar is acceptable for any signed-in user.
- **I2** — Malformed or dangling rows in `menu_overrides` /
  `menu_registry` MUST NOT throw. `applyOverrides` coerces; if anything
  escapes, the `<ErrorBoundary>` around `SidebarContent` catches it and
  renders the "Menu temporarily simplified" fallback.
- **I3** — Empty / failing `menu_access_config` ⇒
  `useMenuAccess.canAccess` fail-open chain (implicit defaults +
  hardcoded `DEFAULT_MENU_ROLES` + admin-last-resort) preserves
  Dashboard, Inbox, Admin core, and Audit core.
- **I4** — Menu Setting / Custom Tabs remain gated by
  `menu_overrides_enabled`. Flipping it to `false` is the kill switch and
  always restores the hardcoded baseline.

## Decision (operational)
- **Production**: `menu_overrides_enabled` stays `false`. Do not re-enable
  until (a) Menu Setting Phase 4 is shipped and (b) the three restoration
  factors are individually validated in a non-prod copy.
- **Code**: temporary build markers (`<meta build-stamp>`,
  `console.info("[build] ...")`, `data-capa-build` span) removed. The CAPA
  hard-guards and ErrorBoundary stay; only the diagnostic markers go.
- **Tests**: 5 regression tests under `src/test/menu/` lock the four
  invariants. All five must pass for any future Menu Setting / Custom Tabs
  PR to land.
- **Scope lock**: no workflow / scoring / RLS / Safety / Incentive /
  Increment change in this close-out. Safety Phase 8+ remains blocked
  until the suite is green and markers are removed.

## Consequences
- Production sidebar / route behaviour reverts to pre-roadmap baseline and
  stays there until an explicit re-enablement decision.
- Future Menu Setting work MUST run the regression suite before merge.
- Removing this CAPA layer requires meeting the criteria in
  `mem://features/admin/menu-setting-capa`.
