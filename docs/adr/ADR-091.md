# ADR-091 — Cycle-anchor consistency: scope from "year" to "cycle window"

**Date:** 2026-06-30
**Status:** Accepted
**Supersedes:** ADR-090 (invariant scope only — repair/detector helpers retained)

## Context

After ADR-090 landed, monthly rollover broke for Quarterly / Half-Yearly /
Yearly KPIs as soon as a later cycle's rows existed in the same review year.

Reproduction (V.A.V.S.S. Ganapathi Varma, 30-Jun-2026):

1. A June→July rollover materialised `July / August / September 2026` rows
   with `frequency_cycle_start = 'Jul-Sep'` (Q3 window label).
2. The user deleted all June 2026 rows.
3. A subsequent May→June rollover synthesised `frequency_cycle_start =
   'Apr-Jun'` (Q2 window label).
4. The ADR-090 trigger compared the two anchors at the
   `(employee, kpi_name, review_year, frequency)` grain and rejected the
   insert: `Cycle anchor conflict (ADR-090): cannot insert KPI with anchor
   Apr-Jun, existing rows in same year use Jul-Sep`.

Root cause: `frequency_cycle_start` is generated **per row as the current
cycle's window label** (`resolve_cycle_anchor(frequency, month_idx)`), but
ADR-090 treated it as a **yearly series tag**. The two semantics coincide
for offset Bi-Monthly cases (where every cycle in the year shares the same
series start, e.g. `Feb-Mar`) — that's why ADR-088's test data didn't
expose the ambiguity — but diverge for Quarterly / Half-Yearly where each
cycle has a genuinely different window label.

## Decision

The intra-year consistency invariant is **narrowed from "one anchor per
year" to "one anchor per canonical cycle window"**.

1. New immutable helper `public.expand_cycle_window_months(frequency,
   anchor) → text[]` returns the full list of month names covered by an
   anchor (e.g. `Quarterly + 'Apr-Jun' → {April, May, June}`).
2. `public.enforce_intra_year_cycle_anchor_consistency()` now rejects an
   insert only when an existing row whose `review_period` falls **inside
   the new row's cycle window** carries a different anchor.
3. `public.detect_intra_year_cycle_anchor_drift()` returns one row per
   `(employee, kpi_name, review_year, frequency, canonical_window)` tuple
   that has more than one anchor — false positives across different
   cycle windows are eliminated.
4. `public.repair_intra_year_cycle_anchor_drift()` scopes oldest-row-wins
   to the canonical cycle window. Audit metadata stamps
   `policy='ADR-091'`, `strategy='oldest_row_wins_per_window'`,
   `cycle_window=<window>`.
5. The detector signature changed (`cycle_window text` column added) and
   was therefore dropped + re-created in the same migration.

## Consequences

- Monthly rollover succeeds even when a later cycle's rows already exist
  in the same year. Deletion-and-re-rollover scenarios behave naturally.
- The Sajid / Prabhat offset Bi-Monthly drift case (ADR-088 / ADR-090) is
  still blocked: the conflicting rows live in the **same** cycle window
  and the new predicate still trips on them.
- ADR-087 client-side anchor resolution is unaffected — anchor remains
  a per-row window label, which is what the renderer already expects.
- No historical data mutation; trigger replacement is non-destructive
  and the legacy ADR-090 SQL is preserved in this ADR for rollback.

## Rollback

Restore the ADR-090 trigger and detector signatures from
`supabase/migrations/<2026-06-28 ADR-090 migration>.sql`. No data
rewrite required; rollback is instantaneous.
