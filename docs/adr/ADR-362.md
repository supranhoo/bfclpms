# ADR-362: Previous-Month Period Default for Data-Entry Surfaces

## Status
Accepted — 2026-09-05

## Context
Teams always enter KPI data for the month that has just ended. Team Reviews
(dashboard team view) and Org KPI Data Entry both defaulted to the **current**
calendar month, so users routinely had to switch the selector back one month
and risked accidental submissions against the current month.

## Decision
Data-entry surfaces default to **current month − 1**:

- New shared helper `getPreviousMonthPeriod(date?)` in `src/lib/previousPeriod.ts`
  returns `{ month, year }` for the prior calendar month, handling the
  January → December-of-prior-year rollover (via date-fns `subMonths`).
- **Team Reviews**: `useDefaultPeriodSelection()` in
  `src/components/ui/ReviewPeriodSelectorEnhanced.tsx` uses the helper.
  This hook is consumed only by Dashboard/Team Reviews.
- **Org KPI Data Entry** (`src/pages/admin/OrgKpiDataEntry.tsx`): uses the
  helper directly for its initial state. The shared `useReviewPeriodDefaults`
  hook is intentionally **not** changed, so Audit Logs, Org KPI Overview and
  Org KPI Audit Review keep current-month defaults (report/audit convention).

## Edge cases
- January defaults to December of the previous year.
- Month-end dates (e.g. Mar 31 → February) are safe via `subMonths`.
- Governance locks on the previous month are handled by existing lock UI.
- URL deep links (`?period=&year=`) continue to override the default.

## Tests
- `src/tests/previousPeriod.test.ts` — mid-year month, January rollover,
  month-end, leap-year February.

## Consequences
- Users land on the month they are actually entering data for; one less
  manual step and no accidental current-month submissions.
- Any future data-entry surface should use `getPreviousMonthPeriod`;
  report/audit surfaces should keep current-month defaults.
