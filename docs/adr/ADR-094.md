# ADR-094 — Edge function reads must paginate (PostgREST 1,000-row cap)

Status: Accepted (2026-06-29)

## Context

Upendra reported that for "Metal Sizing" (June 2026) the Incentive Data
Entry Grid showed ₹3,98,134 across 280 employees, while the Incentive
Report Preview computed only 201 records totalling ₹3,10,983.
Diagnostics in the dialog read: *In scope 292 · With daily 1000 · With
rate 175 · Skipped (no rate) 0* — the exact value `1000` was the smoking
gun.

## Root cause

`supabase/functions/compute-monthly-incentives/index.ts` fetched
`production_daily_entries`, `incentive_production_rates` and
`employee_incentive_records` (override probe) with bare `.select()`
calls. PostgREST silently caps any unbounded select at 1,000 rows.
Daily-entry rows for the programme/month exceeded 1,000, so ~91
in-scope employees (incl. Pavan Gope, 1050 TPD) were dropped from the
compute pass and ₹87,151 of incentive disappeared from the Report.

The same defect class was previously documented for the `profiles`
global query (RCA 2026-05-29, comment at index.ts:358) — that audit
missed these three sibling reads.

## Five Whys

1. Report total < Data Entry total → compute saw fewer employees.
2. Compute saw fewer employees → `prodDailyMap` was incomplete.
3. `prodDailyMap` was incomplete → the source fetch returned exactly 1000.
4. Fetch returned 1000 → no `.range()` loop; PostgREST hard-capped.
5. No pagination → the 2026-05-29 RCA only paginated the queries it
   investigated; no repo-level guard prevented regression.

## Decision

- All three reads now loop via `.range(from, from + PAGE - 1)` with
  `PAGE = 1000`, breaking on a short page. This matches the existing
  paginated read at index.ts:60 (`incentive_program_mappings`).
- Diagnostics carry `daily_entries_rows_loaded` and
  `production_rate_rows_loaded` so the symptom would surface
  immediately next time.
- `src/test/computeMonthlyIncentivesPagination.test.ts` pins the
  contract — any future regression that removes `.range()` from these
  reads fails the build.
- `POLICY.md` codifies: every Supabase read in an edge function that
  can exceed 1,000 rows MUST paginate.

## Consequences

- Production-incentive Reports for any programme/month with >1,000
  daily-entry rows now match the Data Entry Grand Total.
- Operational repair is a re-run of **Confirm & Compute** for the
  affected period — the compute function already deletes-then-upserts.
- No schema, RLS, or UI redesign. Reads are O(N/1000) round-trips.

## Rollback

Revert the function file and redeploy; pagination is the only
behavioural change.
