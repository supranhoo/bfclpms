# ADR-308 — Dependency-aware, audited deletion of organisation master records

- **Status:** Accepted
- **Date:** 2026-08-21
- **Version:** v2.66.308
- **Policy:** POLICY §ORG-MASTER-DELETE-DEPENDENCY-GUARD

## Context

A division named `CLU` was created by mistake. Deleting it from System Settings >
Organization failed with:

```text
Failed to delete: update or delete on table "divisions" violates foreign key
constraint "access_profile_org_scope_division_id_fkey" on table "access_profile_org_scope"
```

Verified facts:

- `CLU` (`23f8f563-047a-4e9f-a627-0bcbad26d832`) had **no employees**, so the list badged
  it "Unused" and offered deletion.
- It was referenced by **3 rows** in `access_profile_org_scope` — the Auditor, Management
  and Onboarding access profiles.
- `divisions` is referenced with NO ACTION (RESTRICT) from `access_profile_org_scope`,
  `production_targets`, `incentive_slabs`, `kpis` and `org_kpi_values`.

## Five Whys

1. Why did the delete fail? A RESTRICT foreign key still pointed at the row.
2. Why was the reference present? Access-profile visibility scopes referenced the division.
3. Why did the user not know? Nothing in the UI listed non-employee references.
4. Why not? "Usage" was measured only by employee count, and labelled "Unused".
5. Why was there no guard? Deletion was a raw client table delete with no server
   preflight, no cleanup path and no audit — the database error was the only feedback.

## Decision

1. **Server-side impact report** — `public.org_master_delete_impact(p_type, p_id)` walks the
   real foreign keys of the target table and returns child table, column, delete action,
   row count, sample labels, and a classification:
   - `blocking` — operational data; must be reassigned by a human.
   - `cleanable` — configuration-only references listed in
     `public.org_master_cleanable_dependencies`.
   - `auto` — already cascaded by the database.
2. **Guarded delete** — `public.org_master_delete(p_type, p_id, p_cleanup)` is admin-only,
   `SECURITY DEFINER`, `search_path` pinned. It refuses when any blocking dependency
   exists, refuses cleanup unless `p_cleanup` is true, deletes cleanable rows first, then
   the record, then appends to `public.org_master_delete_audit` (append-only) with actor,
   entity type/name and the cleaned counts.
3. **Honest UI** — `src/services/organization/orgMasterDelete.ts` wraps both RPCs and maps
   table names and server errors into plain language. The confirmation dialog lists
   dependencies, disables Delete while blockers exist, and requires an explicit checkbox
   before configuration references are removed. Employee-count badges now read
   "No employees".

## Consequences

- No operational data is ever silently deleted; blockers are named, not guessed.
- Cleanable dependencies are configured in a table, honouring the zero-hardcoding rule —
  adding a new safe-to-clean reference is a data row, not a code change.
- Every organisation master deletion is now attributable.
- `CLU` was removed through this exact path; the audit row records the three cleaned
  access-profile scope rows.

## Risk and rollback

- **Data:** additive tables plus two new functions; no existing constraint loosened.
- **Security:** admin-only, definer-safe, cleanup gated server-side.
- **Regression:** `src/test/orgMasterDelete.test.ts` (7 tests) covers classification, the
  CLU shape, label safety, error mapping and the server guard contract.
- **Rollback:** drop the two RPCs and the registry/audit tables, revert
  `src/pages/admin/Organization.tsx` and delete the service file.

## Amendment — ADR-308a (2026-08-21, v2.66.308a): cascade-aware impact

Deleting the duplicate business unit `HR-HUMAN RESOURCES`
(`95b992c9-42cf-4030-91db-7fadf42afb67`) still failed. Verified facts:

- The BU itself: no employees, no KPIs, 3 cleanable access-profile scope rows,
  11 safety incidents (SET NULL), 1 CASCADE child department **Executive**.
- `Executive` is referenced by **2 `org_kpi_values`** rows (Feb-2026 and Mar-2026
  "Adherence to Manning Norms", status `propagated`) and 3 access-profile scope rows,
  both under RESTRICT.

The original impact report walked only foreign keys pointing directly at the target, so
the cascade child's own blockers were invisible and the delete aborted mid-transaction.

**Decision**

1. `public.org_master_delete_impact_at(table, id, path, depth)` — recursive, depth-capped
   (4), cascade sets over 200 rows skipped, cycle-safe by depth. It follows `CASCADE`
   children and reports their dependencies with a `via_path` naming the child.
2. `public.org_master_delete_impact` delegates to it and returns three new columns:
   `via_path`, `target_table`, `target_id`.
3. `public.org_master_delete` blocks on descendant blockers before deleting anything, and
   deletes cleanable rows using `target_id` (the record they actually hang off), recording
   the path in the audit `cleaned` payload.
4. UI: the dialog shows "Deleting this also removes: Departments: Executive" and appends
   "(on Departments: Executive)" to each blocker.

**Consequences** — stricter and honest: records that previously appeared deletable and
then failed are now reported as blocked, naming exactly what to move. `HR-HUMAN RESOURCES`
remains blocked until its two Executive-department Org KPI values are reassigned or removed.

**Regression** — `src/test/orgMasterDelete.test.ts` (11 tests) covers the HR shape,
`via_path` rendering, and the recursive-walk migration contract.
