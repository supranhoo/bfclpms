# ADR-107: Remove invalid KPI relationship columns from `can_send_notification_to`

**Date:** 2026-07-17
**Status:** Accepted

## Symptom
Assisted Submission Verification (and every non-admin cross-user notification insert) failed with `42703 column k.assigned_to does not exist`. Reported by Pankaj Sahu (CLU Operation).

## Root cause
`public.can_send_notification_to` inferred sender relationships from columns that do not exist on `public.kpis`: first `k.assigned_to`, then `k.manager_id`, `k.skip_manager_id`, `k.hr_id`, `k.auditor_id`, and `k.management_id`. Admin/HR paths short-circuited earlier and masked the bug in smoke tests.

## 5-Why
1. Submission failed → notifications INSERT raised 42703.
2. Trigger calls `can_send_notification_to` which SELECTs from `kpis k`.
3. `kpis` has none of the assumed reviewer columns; it only stores `employee_id` for this relationship domain.
4. Hardening migration was authored from a generic "assignee" mental model rather than the live schema.
5. Previous regression test only asserted `d.head_user_id`; it did not guard the `kpis` alias.

## Fix
- Migration: removed the invalid KPI relationship branch. Profile/organization hierarchy handles managers and heads, the management role remains globally authorized, and `audit_kpi_assignments` handles auditor scope.
- Widened `src/test/notificationsSenderRelationshipSchema.test.ts` to reject all nonexistent KPI reviewer fields and validate every qualified column against a maintained schema fixture.

## Follow-up
Any future column referenced inside `can_send_notification_to` must be verified against `information_schema.columns` before merge.
