# ADR-082 — Streaming chunked table export in `create-backup`

## Status

Accepted — 2026-06-09.

## Context

From 2026-06-04 through 2026-06-09, every scheduled backup landed as `failed`
with `Coverage shrink: 201/203 tables backed up` and a repeating
`Batch 46/51 transient: HTTP 546` in `backup_logs.error_message`. The
halved sub-batch retry (Phase 9.2 WP-b, `BATCH_SIZE_RETRY=2`) recovered
sub-batch 2 but sub-batch 1 (`notifications` + `org_kpi_data_entry_logs`)
failed deterministically after both retries.

`notifications` (~78k rows, 67 MB) and `org_kpi_data_entry_logs` (~85k rows,
57 MB) are the two largest tables in the database. The previous
implementation accumulated every row of a table into one in-memory array
(`fetchAllRows`) and then serialised the whole array (`JSON.stringify(rows)`)
before upload. Peak heap = (row array) + (full JSON string) +
(`TextEncoder` byte buffer) routinely exceeded the 256 MB Deno Deploy
worker cap, regardless of `BATCH_SIZE` or `BATCH_SIZE_RETRY`.

Earlier CAPA cycles addressed concurrency (`BATCH_SIZE=4`), transient
rate-limit retries, and partial-coverage visibility (`backup_hard_fail_on_partial`).
None of them addressed the per-table memory shape.

## Decision

1. `create-backup` exports each table by streaming pages of `PAGE_SIZE = 1000`
   rows from Postgres and flushing a part file to storage every
   `ROWS_PER_CHUNK = 5000` rows.
2. Part files use the naming convention `<table>.part-NNNNNN.json` in the
   same backup folder.
3. The manifest table entry now carries an authoritative `files: string[]`.
   `file` is retained as the first part path for backward-compatible readers.
4. `verifyBackupIntegrity` sums row counts across all part files of a
   table and flags missing parts individually.
5. `restore-backup` iterates `entry.files` (falling back to `[entry.file]`
   for older backups) and upserts each part independently. Legacy
   single-file backups remain restorable unchanged.
6. `BATCH_SIZE_RETRY` is tightened from `2` → `1` so a transient failure
   isolates to a single table instead of dragging a healthy sibling into
   the retry budget.
7. Retry telemetry now includes the table list for each failing sub-batch
   so admins can identify the offending table from `backup_logs.error_message`.

Peak heap during export is now bounded by `ROWS_PER_CHUNK` (typically
< 8 MB JSON for PMS row shapes) rather than total table size.

## Consequences

- New scheduled backups produce many small `.part-NNNNNN.json` files per
  large table instead of one big `.json`. Storage cost is unchanged in
  aggregate; object count grows.
- Restore must round-trip both formats: legacy `<table>.json` and new
  `<table>.part-NNNNNN.json`. Both are tested via I17.
- Integrity verification cost scales with part count, not table size.
- `BATCH_SIZE = 4` (primary) and `RETRY_BUDGET_MS = 8min` are unchanged
  to preserve Phase 9.1 / 9.2 invariants.
- Hard-fail-on-partial remains the terminal authority (Phase 9.2 WP-a).

## Rollback

Revert `supabase/functions/create-backup/index.ts`,
`supabase/functions/restore-backup/index.ts`, `src/hooks/useBackups.ts`,
and `src/test/safety/phase9/backup-coverage-contract.test.ts` to the
pre-ADR-082 commit. Existing chunked backups created under ADR-082 will
no longer restore because legacy restore expects `<table>.json`, but
older backups remain restorable. Re-run a fresh scheduled backup after
rollback.
