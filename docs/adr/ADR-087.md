# ADR-087 — Client/DB parity for multi-month `frequency_cycle_start`

**Date:** 2026-06-10
**Status:** Accepted

## Context

Org KPI Data Entry (`/admin/org-kpi-data`) was listing Bi-Monthly KPIs with
`frequency_cycle_start = 'May-Jun'` on the **May** page. The Propagate action
then failed with *"Bi-Monthly KPI cannot be reviewed for May. Only the
terminal month of the cycle is reviewable."*

Root cause: `resolveEffectiveCycleOption` in
`src/lib/frequencyCycleOptions.ts` only matched `frequency_cycle_start`
against the hardcoded `BI_MONTHLY_OPTIONS` (`Jan-Feb`, `Feb-Mar`). When the
stored anchor (e.g. `May-Jun`, `Mar-Apr`, `Mar-May`, `Aug-Oct`, `Nov-Apr`)
wasn't in that list, the resolver silently fell back to the global
`frequency_config` row's `sub_frequency` mapping or to `options[0]`. The
resulting `lockedMonths` no longer matched the KPI's real cycle, so the UI's
`isKpiLockedForPeriod` filter let the card through. Meanwhile the DB trigger
`enforce_frequency_lock_on_submission` reads `frequency_cycle_start` literally
and correctly blocked the write.

## Decision

1. Add `deriveCycleOptionFromCycleStart(frequency, cycleStart)` that builds a
   synthetic `CycleOption` (lockedMonths + activeMonth) for any anchor,
   mirroring the DB trigger math:
   `cycle_pos = ((month - start_month) mod 12) mod cycle_length`; terminal
   month is the one at position `cycle_length - 1`.
2. Extend `resolveEffectiveCycleOption` to call the new helper **before**
   falling back to the global-config / first-option path whenever a per-KPI
   `kpiCycleStart` is supplied. Hardcoded matches (`Jan-Feb`, `Feb-Mar`,
   `Jan-Mar`, etc.) still win and are unchanged.
3. No DB changes. The trigger remains the source of truth.

## Consequences

- Org KPI Data Entry no longer shows multi-month KPI cards on non-terminal
  months. The Propagate failure path the user hit is now unreachable.
- `isKpiLockedForPeriod` returns the same answer the DB would. MyKpis,
  Team Reviews, and any other consumer of the helper inherit the fix
  transparently.
- Behaviour for KPIs whose `frequency_cycle_start` already matched a
  hardcoded option is unchanged.
