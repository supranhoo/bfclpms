# ADR-202 — Import errors must be observable end-to-end

Status: Accepted (2026-07-30)

## Context

An Employee import of 4 rows returned 1 success and 3 failures
(`101393`, `101395`, `101818`). Every failed row showed the same message:
*"Edge Function returned a non-2xx status code"*. No `profiles` rows were
created, and `create-employee` edge logs contained only
`Auth header present` → `User validated: 535d9a14…` for the three failed
invocations — no error line at all.

## Root cause

Two independent observability gaps stacked:

1. **Client.** `ImportData.tsx` calls
   `supabase.functions.invoke('create-employee', …)`. On a non-2xx the SDK
   returns `data = null` plus a `FunctionsHttpError` whose `.message` is the
   fixed placeholder; the JSON body sits unread on `error.context`. The code
   did `fnData?.error || fnError.message` — `fnData` is always `null` on that
   branch, so the server's message was discarded.
2. **Server.** `create-employee` had three non-2xx returns with no logging:
   `400 Unknown employee category`, `400 Unknown employment status`, and
   `403 Unauthorized`. The caller was the admin id, so the failures were one
   of the two 400 validation rejections — but the offending value was never
   recorded anywhere.

Contributing factor: `employee_categories` rows are all bound to company
`BFCL`, while three companies exist. The edge function accepts a category
only when it is global or matches the row's company; the importer pre-flight
matched on **name only**, so a cross-company row passed the preview and then
failed server-side with an opaque error.

## Five Whys

1. Import showed a placeholder error → the UI printed the SDK message.
2. It printed the placeholder → `fnData` is `null`, so the body was unreachable.
3. It wasn't caught server-side → the 400s returned without logging.
4. The 400 fired → a master-data value failed strict validation.
5. The preview didn't catch it → pre-flight validation was not company-aware,
   unlike the server rule it was supposed to mirror.

## Decision

- `src/lib/edgeFunctionError.ts` exposes `extractFunctionError(fnError, fnData)`,
  which reads `fnError.context` and returns the server's `error`/`message`
  field, falling back to raw text and finally to the SDK message.
  `ImportData.tsx` uses it at the `create-employee` invoke site.
- `create-employee` logs a `[create-employee] REJECT <status>` warning with the
  employee code, offending value, resolved `company_id`, and the candidate
  master rows before every validation/authorisation rejection.
- The category 400 now distinguishes "no such name" from "exists but belongs to
  another company", and names the admin screen that fixes it.
- The importer pre-flight mirrors the server's company-scope rule: a category
  bound to a different company is flagged in the preview, before any network call.

## Consequences

- The Import Results **Issues** table (and the Download Error Report CSV) now
  carries the real reason for every failed row.
- Cross-company category mismatches are caught in the preview step at zero
  network cost.
- Locked by `src/test/edgeFunctionError.test.ts` (7 tests) and
  `src/test/importCategoryCompanyScope.test.ts` (6 tests).

## Rollback

Revert `src/lib/edgeFunctionError.ts`, the two `ImportData.tsx` hunks, and the
edge function, then redeploy. No schema, RLS, trigger, or data change.
