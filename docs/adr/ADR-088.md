# ADR-088 — Cycle anchor preservation across monthly rollover

**Date:** 2026-06-10
**Status:** Accepted
**Related:** ADR-086 (multi-month re-percolation), ADR-087 (client-side cycle anchor resolution)

## Context

Prabhat Kumar Singh's Bi-Monthly "Achieve organization's production target"
KPI was authored with `frequency_cycle_start = 'Feb-Mar'` (offset cycle:
Feb-Mar / Apr-May / Jun-Jul / …). After two monthly cron rollovers the column
had drifted to `May-Jun` for May 2026 and June 2026, producing **overlapping
cycle windows** within the same org-KPI tuple — the same KPI showed
`Bi-Monthly: Apr-May` in April and `Bi-Monthly: May-Jun` in May.

Two co-located resolvers were hard-coded to standard Jan-anchored cycles
and silently overwrote the per-KPI offset anchor:

1. Edge function `auto-rollover-kpis` — `buildNewKpi` called
   `resolveCycleAnchorForPeriod(frequency, targetMonth)` first and only fell
   back to the source anchor when the resolver returned null (never, for
   multi-month frequencies).
2. DB function `public.resolve_cycle_anchor(frequency, month_idx)` used the
   same Jan-anchored math; `repair_org_kpi_cycle_anchors` would actively
   rewrite valid offset anchors to the standard one.

Other employees on the same tuple kept the correct anchor because their
rows were created by `materialize_kpis_for_org_kpi` or `admin_bulk_apply`,
both of which copy the source row's anchor verbatim.

## Decision

The per-KPI `frequency_cycle_start` is **immutable across rollover** and
across automated repair. The only legal mutation paths are admin overrides
(KPI editor, KRA library propagation) and originator inserts.

1. `auto-rollover-kpis::buildNewKpi` now reads
   `source.frequency_cycle_start ?? resolveCycleAnchorForPeriod(...)`.
   Existing anchors are preserved; synthesis only runs when the source has
   no anchor at all.
2. New DB helper `public.is_valid_cycle_anchor(frequency, anchor)` plus a
   3-arg overload `public.resolve_cycle_anchor(frequency, month_idx,
   existing_anchor)` that returns the existing anchor when it is valid for
   the frequency and only falls back otherwise. The 2-arg signature is kept
   for backwards compatibility.
3. `repair_org_kpi_cycle_anchors` calls the 3-arg sticky resolver, so it
   never rewrites a legitimate offset anchor.
4. New admin-only RPC `public.detect_org_kpi_cycle_anchor_drift()` lists
   tuples whose rows disagree on `frequency_cycle_start` within the same
   review year — used by the admin "Cycle Anchor Repair" page to surface a
   warning banner.

## Consequences

- Offset Bi-Monthly (`Feb-Mar`), offset Quarterly (`Apr-Jun`/`Jul-Sep`),
  offset Half-Yearly (`May-Oct`) and offset Yearly (`Apr-Mar`/`Jul-Jun`)
  cycles are now preserved across monthly cron rollovers.
- ADR-087 client-side locking and ADR-086 multi-month percolation now have
  a stable anchor SSOT to read against, so the May/June terminal-month
  drift cannot recur for the same tuple.
- Legacy rows whose anchor is `NULL` still receive a synthesised standard
  anchor on rollover — there is no regression for non-offset KPIs.

## Repair

One-shot scoped reset of Prabhat's May 2026 and June 2026 rows back to
`Feb-Mar`, audited as `KPI_CYCLE_ANCHOR_REPAIRED` with
`policy = 'ADR-088'`. No score/submission/OKV mutation. Broader backfill
is deferred until the new detector has run for ≥1 cron cycle.
