# ADR-073 — iOS Safari `history.replaceState` throttle hardening

- Status: Accepted
- Date: 2026-06-05
- Owners: Platform / Dashboard

## Context

Auditor user `auditor001` (Shekhar Sharad) reproducibly crashed the
`/dashboard` route on iPhone / iPod (iOS Safari 18.2) while working
normally on Android Chromium. The diagnostic sink added in the previous
turn (`public.client_error_reports`) captured the exact error:

> `Attempt to use history.replaceState() more than 100 times per 10 seconds`

iOS WebKit enforces a hard cap of 100 `history.replaceState()` calls
per 10 s window and throws once exceeded. Chromium has no such cap,
which explained the platform asymmetry.

Code review pinpointed the source: `useUrlFilterState` /
`useUrlFilterStateNullable` (used by `EmployeeSelectorGrid` and
`Dashboard`) called `setSearchParams((prev) => …, { replace: true })`
on every setter invocation — including no-op cases where the resulting
URL was byte-identical to the current one — and multiple synchronous
setter calls in the same tick each produced a distinct write.

## Decision

Harden `src/hooks/useUrlFilterState.ts` with three additive,
behaviour-preserving safeguards:

1. **No-op guard.** Compare the requested next value against the
   current `searchParams.get(paramName)` and return early if unchanged.
2. **Microtask coalescer.** Module-scoped queue + `queueMicrotask`
   flush composes all pending mutators into a single `setSearchParams`
   call. Affects `useUrlFilterState`, `useUrlFilterStateNullable`, and
   `useClearAllFilters`.
3. **Rolling rate-limit.** Cap real flushes at 60 / 10 s (40 % below
   Safari's 100 / 10 s throttle). Excess flushes defer to the next
   animation frame and re-merge any further setter calls that arrive
   in the meantime, so the final URL still matches the last intent.

`Dashboard.tsx` narrows the mentioned-kpi cleanup effect dep array from
`[searchParams]` to `[searchParams.get('mentioned_kpi'),
searchParams.get('mentioned_employee')]` so the effect no longer re-runs
on every unrelated URL change. The deep-link processor at line 241
intentionally retains `[searchParams]` because it must observe any URL
form on mount; it is idempotent via `deepLinkProcessedRef`.

## Consequences

- Public API of all three hooks is unchanged.
- All URL persistence (filters, view mode, selected employee, page,
  size) still works identically — visually no change.
- iOS `/dashboard` cannot reach the 100 / 10 s ceiling under any
  combination of filter typing, mode switching, and deep-link cleanup.
- All other browsers see strictly fewer history writes; no regression
  surface.

## Policy

Direct calls to `setSearchParams` or `window.history.replaceState` from
feature code are prohibited for URL-persisted filter / view / selection
state. Use `useUrlFilterState`, `useUrlFilterStateNullable`, or
`useClearAllFilters` so writes flow through the coalescer.

## Verification

- New unit suite `src/test/useUrlFilterState.test.tsx` (6 tests, all
  green) covers no-op guards, cross-hook coalescing, nullable
  idempotency, no-op `useClearAllFilters`, and the 200-call burst case.
- Existing Menu CAPA / scorecard / safety / RLS suites remain green.
- Telemetry table `public.client_error_reports` stays live; success is
  zero new `replaceState` rows for `account_code = 'shekhar.sharad'`
  on iOS after publish.

No DB / migration changes to undo.
