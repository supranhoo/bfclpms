# ADR-064 — Group-Based KPI Scoring Architecture

- **Status:** Proposed (paired with `docs/prd/PRD-group-scoring.md` v1.0)
- **Date:** 20 May 2026
- **Supersedes:** none
- **Related:** ADR-055, ADR-061, ADR-062, POLICY §88, §111

## Context
Per-employee scoring at 50-emp departments produces ~4,200 cell-actions per cycle. ~60% of KPIs are departmentally identical, but the workflow forces row-by-row grading at every reviewer stage. Org KPI propagation solves only the *Data Owner write*; reviewers still grade individually.

## Decision
Reuse the existing Org KPI propagation primitive (`propagate_org_kpi_value`) and snapshot reader (`get_org_kpi_data_entry_snapshot`) to power a new reviewer-facing **Bulk Scoring Grid** for Manager, Auditor, HR PMS, Skip-Level, and Management stages.

- Add `kpi_group_type` (`individual` / `departmental` / `org`) to `kpis` and denormalise to `review_submissions`.
- Add `is_group_override` + `group_write_batch_id` to `review_submissions` (audit linkage, override traceability).
- Add `bulk_score_batches` (summary per batch, no FK to `auth.users`).
- Add RPC `bulk_advance_workflow_stage(emp_ids[], stage, period, year)` — SECURITY DEFINER, mirrors single-employee path's POLICY §88 guards.
- Extend `propagate_org_kpi_value` to accept a `stage` parameter so reviewer-stage writes share the same skipped-reason taxonomy as Data Owner propagation (POLICY §111.6).

## Reuse, not rebuild
| Surface | Reused |
|---|---|
| Read path | `get_org_kpi_data_entry_snapshot` (extended) |
| Write path | `propagate_org_kpi_value` (stage param added) |
| Cell status | `deriveScopedRowStatus` / `deriveOrgKpiTileStatus` |
| Canonical key | `canonicalGroupKey` |
| Workflow gating | `workflow_config`, per-employee resolved status |
| Audit | `system_audit_logs` (batch + per-cell linkage) |
| Notifications | Notification & Dispatch Engine (batched per batch_id) |
| Backup | `get_backup_table_order()` — `bulk_score_batches` auto-included |

## Consequences
- **Positive:** ~80% click reduction; consistent dept scoring; explicit override signal; one batch-linked audit row; no schema rewrite of `review_submissions`.
- **Negative:** Adds 3 columns + 1 table; reviewer mental model expands to handle "group vs override"; mobile reviewers get pager fallback (not native bulk).
- **Mitigations:** auto-detect is advisory only; override rate becomes a QA metric; default `kpi_group_type` is `individual`.

## Rejected alternatives
1. **Materialised "group_score" table** — duplicates source of truth; breaks POLICY §88 / immutability reasoning.
2. **Pure-UI bulk apply (no schema change)** — loses audit linkage; cannot distinguish group write from individual write later.
3. **Replace per-employee scoring entirely** — destroys individual accountability; abandons existing workflow engine.

## Addendum — v1.1 (2026-05-20): Click-to-Load Architecture

Adopted to bound Cloud compute cost and meet a <400 ms first-paint target on `/review/bulk-scoring`.

### Decision
1. The dashboard mounts as an **empty shell**. No `kpis` / `review_submissions` reads occur on mount or on filter change.
2. Filter changes fire only a lightweight count RPC `bulk_scope_preview(filters)` that returns `{emp_count, kpi_count, pending_cells, est_payload_kb}` from index-only paths.
3. Grid hydration requires an explicit **Load Scope** click that calls paged RPC `bulk_scoring_snapshot(filters, page, page_size=200)` returning server-projected slim rows (~80 B/row).
4. A hard cap rejects loads where `emp_count × kpi_count > 25,000` or `est_payload_kb > 5 MB`.
5. No realtime subscriptions on this page; refresh is manual (POLICY §120 §5).
6. Row + column virtualization via `@tanstack/react-virtual` is mandatory.

### RPC budget
| RPC | p95 target | Notes |
|---|---|---|
| `bulk_scope_preview` | 80 ms | Index-only counts, no row payload |
| `bulk_scoring_snapshot` | 900 ms | 200 KPI-rows × ≤200 employees, slim cols, gzip |
| `kpi_cell_detail` | 250 ms | On-demand drill |
| `propagate_org_kpi_value` (stage) | 1.2 s @ 100 cells | Single tx, POLICY §88 skip |
| `bulk_advance_workflow_stage` | 1.5 s @ 200 emps | Stage transition only |

### Rationale
- Replaces today's N+1 fetch pattern (`useKpiEmployeeMatrix` issues many `.in()` batches) with one server-projected RPC.
- Defers all heavy reads to explicit user intent → predictable Cloud CPU usage.
- Stale-while-revalidate (`(filters, period)` keyed, 5 min) eliminates round-trips when reviewers toggle between scopes.

### Rejected alternatives (v1.1)
1. **Auto-load on filter change** — guarantees CPU spikes on cascade interactions.
2. **Client-side join over `useKpiEmployeeMatrix`** — fails at >2k cells, no server projection.
3. **Realtime channel for grid** — N reviewers × M cells produces inbox/CPU storm; deferred to Phase 2.
