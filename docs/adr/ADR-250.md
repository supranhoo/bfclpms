# ADR-250 — Storage performance & preview resilience

## Date
2026-08-04

## Status
Accepted

## Context
Reviewers reported evidence files taking very long to preview, intermittently
ending in "The connection to the database timed out" or a misleading
"You do not have access to this file" toast.

Measurements:
- `pg_stat_statements` ranked the unfiltered `kpis` read from `useAllKpis` as
  the #1 query by total time: 267,953 calls, 591 ms mean, 7.95 s max against
  the 8 s `authenticated` `statement_timeout`, 158,373 s cumulative.
- Evidence objects average 275 KB, so bandwidth was not the bottleneck.
- The preview dialog buffered each object into a Blob before rendering.
- `normalizeEvidenceError` mapped every non-specific failure to access-denied.

## Decision
1. `useAllKpis` reads through `public.get_all_kpis_slim()` — a STABLE SECURITY
   DEFINER RPC mirroring `get_reviewer_kpis_for_period`, PK-ordered and paged
   with `fetchAllRpcPaged`. Visibility rules are unchanged (full access for
   admin/auditor/hr_pms/management/report-override, otherwise self + direct +
   indirect reports).
2. Evidence previews resolve a 10-minute signed URL and stream, with a 20 s
   timeout and an explicit Retry button.
3. `review-evidence` SELECT policies call the new
   `public.can_read_kpi_evidence(uuid)` helper, which caches `(select auth.uid())`
   per statement instead of re-deriving it per row.
4. Error normalisation distinguishes transient backend pressure from denial.

## Consequences
- Full-table KPI reads collapse from ~21 RLS-heavy pages to one guarded scan.
- Storage requests stop queueing behind saturated Postgres.
- A slow preview now shows a truthful message and a retry, never a false
  permission error.
- Rollback: revert `useAllKpis` to the paged `SLIM_KPI_SELECT` read and restore
  the previous storage policies; both new functions are additive.
