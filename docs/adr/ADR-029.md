# ADR-029: Scope-Aware Propagation Validation

## Status
**Accepted**

## Date
2026-03-30

## Context
The Org KPI Data Entry Propagate button needed validation logic to determine when propagation is allowed. Org KPIs can be scoped at organization, department, or employee level, each storing achieved values differently.

## Decision
The Propagate button uses scope-aware validation:
- **Organization scope:** enabled when top-level `achievedValue` is non-empty OR entry is marked N/A
- **Department/Employee scope:** enabled when at least one `scopedValues` row has a non-null `achievedValue` OR is marked N/A

Both the Propagate button AND the blank-data propagation guard must preserve this scope-aware logic.

## Alternatives Considered

### Alternative A: Check only top-level field for all scopes
- **Description:** Use a single `achievedValue` check regardless of scope type
- **Rejected because:** Scoped KPIs store values in per-department/per-employee rows, not in the top-level field. This would permanently disable propagation for all scoped entries.

### Alternative B: Disable validation entirely (always allow propagation)
- **Description:** Remove the guard and let admins propagate at any time
- **Rejected because:** Propagating empty/null values would overwrite existing employee scores with blanks, causing data loss.

## Consequences

### Positive
- Scoped KPIs can be propagated correctly
- Prevents accidental blank-data propagation

### Negative
- Slightly more complex validation logic to maintain

### Neutral
- Validation runs client-side before the RPC call
