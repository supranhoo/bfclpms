# ADR-112 — Bidirectional notification sender authorization

**Status:** Accepted (2026-07-17)
**Related:** POLICY §108 (Notification Recipient Guard), §108b (Sender Authorization Matrix), migration `20260717063237` (original guard).

## Context

`public.can_send_notification_to(sender, target)` was introduced to prevent any authenticated user from spoofing notifications to arbitrary users. The original implementation only recognised **downward** organisational relationships (sender = target's manager/skip/dept-head/BU-head) and reviewer roles where sender was the reviewer.

Legitimate upward and peer flows — an employee's Annual Review save triggering a notification to their manager, a reviewer handoff between manager/skip/BU/HR — were silently blocked. Because the offending INSERT runs inside an `AFTER UPDATE` trigger (`notify_annual_review_stage_change`), the exception rolled back the parent update. Symptom: "not authorized to send notifications to user …" toast on Annual Review draft save.

## Decision

Extend `can_send_notification_to` to a bidirectional matrix (POLICY §108b):

| Edge | Allowed |
| --- | --- |
| self → self | ✅ |
| admin / hr_pms → any | ✅ |
| any → admin / hr_pms | ✅ |
| manager / skip / dept-head / BU-head → subordinate | ✅ |
| subordinate → manager / skip / dept-head / BU-head | ✅ |
| KPI reviewer (manager/skip/hr/auditor/management) ↔ assignee | ✅ (both directions) |
| AR reviewer (manager/skip/dept/BU/hr) ↔ employee | ✅ (both directions) |
| AR peer reviewers on the same instance | ✅ |
| unrelated users | ❌ |

The notifications RLS `INSERT` policy was also tightened to invoke this guard directly (previously only checked `user_id IS NOT NULL`), closing the privilege-escalation gap even if the BEFORE-INSERT trigger were disabled.

## Rejected alternatives

- Skipping the guard inside `SECURITY DEFINER` contexts — no reliable Postgres flag; would require session GUCs around every trigger.
- Re-invoking every trigger insert as service-role via an edge function — disproportionate refactor.
- Wrapping every trigger INSERT in `EXCEPTION WHEN insufficient_privilege` — hides real authorization bugs.

## Consequences

- Legitimate upward and peer notifications flow again.
- RLS policy now enforces the same rule as the trigger; guard cannot be bypassed by dropping the trigger.
- Any new reviewer relationship added in future must be listed in POLICY §108b and reflected in this function in the same PR.
