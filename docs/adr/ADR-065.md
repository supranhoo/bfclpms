# ADR-065: Server-side scoping RPC for KPI-Employee Matrix report

- Status: Accepted
- Date: 2026-05-22
- Related: ADR-064 (Bulk scoring click-to-load), POLICY §114

## Context

`/reports/kpi-employee-matrix` was fetching every KPI for the selected month with deeply nested PostgREST joins (`kra_categories`, `profiles!kpis_employee_id_fkey(...departments(name))`) and applying Division / BU / Dept / Search filters client-side. For typical months (≈2,000–3,000 KPIs) this exceeded the 8 s Postgres statement timeout (error code `57014`) and surfaced as "No KPI data found".

## Decision

1. Introduce two SECURITY DEFINER RPCs:
   - `rpc_kpi_employee_matrix_scope(period, year, division, bu, dept, category, search)` returns `(employee_id, kpi_count)` after applying all filters server-side using indexed joins (`kpis → profiles → departments → business_units`).
   - `rpc_kpi_employee_matrix_rows(period, year, employee_ids[], category)` returns flat KPI rows for a batch of employees, joining only `kra_categories.name`.
2. Rewrite `useKpiEmployeeMatrix` to: (a) call scope, (b) batch profile fetches, (c) batch rows fetches, (d) batch submissions fetches — never sending a single large nested query.
3. Add `useKpiEmployeeMatrixScope` to power a **click-to-load** affordance: the matrix renders empty until the user presses **Load Matrix**, after seeing the employee/cell count preview.
4. Hard cap at 25,000 cells; if exceeded, prompt the user to narrow filters rather than attempting the fetch.

## Consequences

- Eliminates the timeout for all realistic filter combinations.
- Reduces idle CPU: the page no longer fires a multi-MB query on every filter tweak.
- Keeps the existing scoring fallback chain, weightage formula, RLS, and export behavior unchanged.
- Future report matrices (Variance, Workflow Resolution, etc.) should follow the same scope-RPC + click-to-load pattern when they iterate over >1k rows per period.
