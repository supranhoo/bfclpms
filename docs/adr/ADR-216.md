# ADR-216 — Stage update RLS must resolve the next status via the effective chain

Status: Accepted (July 2026)

## Context
Employee Anil Rajwar (100406) could not submit his annual self review:

```
new row violates row-level security policy for table "annual_review_instances"
```

His instance has `enabled_stages = ["self","dept_head","bu_head"]`, but
`dept_head_id = bu_head_id` (same person). Two components disagreed on the
next status:

- `advance_annual_review_status` resolves it from
  `annual_review_effective_chain(id)` — duplicate/absent reviewers skipped —
  and wrote `pending_bu`.
- The `instances_stage_update` policy's WITH CHECK resolved it from raw
  `enabled_stages` and only permitted `pending_dept`.

Two in-flight instances were sitting on a stage where the two disagreed; the
class of defect recurs for every review whose consecutive stages share a
reviewer.

## Decision
1. New `public.annual_review_allowed_next_status(uuid, annual_review_status)`
   — `STABLE SECURITY DEFINER`, pinned `search_path`. The SECURITY DEFINER
   wrapper is required: `annual_review_effective_chain` is SECURITY INVOKER
   and reads `annual_review_instances`, which a policy on that same table
   cannot reference without recursion.
2. `instances_stage_update` recreated. USING clause unchanged (no widening of
   *who* may act). WITH CHECK now accepts, per reviewer slot, the current
   pending status, the `enabled_stages`-derived next status (backward
   compatible) **or** the effective-chain-derived next status.

## Consequences
- Submissions advance cleanly across auto-skipped stages.
- Actor gating and all other policies are untouched.
- Rollback: recreate `instances_stage_update` without the
  `annual_review_allowed_next_status` disjuncts (verbatim previous definition
  is in the migration header comment).
