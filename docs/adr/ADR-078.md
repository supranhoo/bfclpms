# ADR-078: Review Notes sidebar visibility mirrors DB access config

- Date: 2026-06-06
- Status: Accepted

## Context

The `HR PMS → Review Notes` sidebar entry used a hardcoded role allowlist
containing every role (`admin, hr_pms, manager, skip_level, management,
auditor, employee`). The `/hr/review-notes` page, however, gates access via
`useReviewNoteAccess()` which reads the DB setting
`system_settings.review_action_notes_visibility`. The DB default only grants
`view` to admin/hr_pms/manager/skip_level/management/auditor and lists
`employee` in `view_own_subject`.

Result: employees (e.g. Jyoti Prakash Dwivedi) saw a menu item that opened
straight into an "access denied" page — the exact menu→deny loop POLICY §111
forbids.

## Decision

Wrap the HR PMS collapsible group's `filterByRole` and `staticFilter` with a
small `gateReviewNotes` helper that consults `useReviewNoteAccess()`:

- Show Review Notes if `role ∈ config.view` (full access).
- Show Review Notes if `role ∈ config.view_own_subject` (employee can still
  see notes about themselves).
- Hide otherwise. When Review Notes is the only HR PMS child the user can
  see, the existing `CollapsibleSidebarGroup` empty-state hides the entire
  group automatically.

The page-level gate is unchanged and remains authoritative.

## Consequences

- Roles in the DB `view` list see Review Notes exactly as before.
- Admins can tighten access from System Settings and the sidebar follows
  immediately (no code change).
- For roles outside both lists, the dead-end menu disappears.

## Rollback

Revert the `gateReviewNotes` import/wrapper in `AppSidebar.tsx`. No DB
changes; no migration required.

## Out of scope

- `Data Entry → Org KPI Data Entry` visibility is correctly governed by
  `menu_access_config.data-entry.allowed_roles` and `org_kpi_data_owners`;
  if it appears for a role you don't want, edit that config row from
  `Admin → Menu Access`.
- The "access denied" copy on `/hr/review-notes` could mention
  `view_own_subject` — copy-only follow-up.
