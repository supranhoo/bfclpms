# ADR-350: Action-Aware Menu Access User Overrides

## Status
Accepted / Implemented

## Context
The `menu_access_user_overrides` table was introduced as a per-user visibility escape hatch: an admin can grant a single user access to a menu that their role or profile would not normally reveal. However, the helper `has_menu_write_access(_user_id, _menu_key, _action)` treated the existence of any override row as authorization for **every** action (add/update/delete). Because dozens of RLS policies on business-configuration tables use this helper for INSERT/UPDATE/DELETE authorization, a visibility-only override silently escalated to full write access.

## Decision
Make `menu_access_user_overrides` action-aware by adding `can_add`, `can_update`, and `can_delete` boolean columns.

- New columns default to `false`, so newly-created overrides are view-only unless the admin explicitly grants write actions.
- Existing rows are backfilled to `true` for all three actions so that current users keep their existing access while the grant becomes explicit and auditable.
- `has_menu_write_access` now checks the matching action flag on the override (or falls through to `has_profile_menu_access`).
- The client-side `canPerform` helper in `useMenuAccess.ts` mirrors the same action-scoped override check so the UI only shows action buttons when the user is actually authorized.
- `grantUserMenuAccess` now accepts explicit `canAdd`, `canUpdate`, `canDelete` flags and defaults to `false` for each.

## Consequences
- Visibility overrides no longer imply write access.
- Admins can grant fine-grained per-user, per-menu, per-action rights without creating a full access profile.
- Existing overrides are preserved; admins should audit and downgrade any overrides that only need view access.
- Client and server authorization semantics stay aligned.
