# ADR-132 — Assignment-scoped KPI audit notifications

**Status:** Accepted (2026-07-22)
**Related:** ADR-112, ADR-131, POLICY §108/§108f, migration `20260722102318`.

## Context

KPI manager approval and N/A processing still failed with `not authorized to send notifications to user …` after ADR-131. The rejected recipient was Mayank (`Auditor002`), an active auditor who was not assigned to the affected KPI.

`notify_on_kpi_status_change()` selected every `user_roles.role = 'auditor'` user for `kpi_ready_for_audit`. The authorization guard correctly permits notifications to assigned auditors, not unrelated auditors. The first unrelated recipient therefore rejected the INSERT and rolled back the KPI status transaction.

## Five-Why analysis

1. The KPI status update rolled back because a notification INSERT was rejected.
2. The recipient guard rejected the target because that auditor had no relationship to the KPI or employee.
3. The status trigger nevertheless included that user because it broadcast to the global auditor role.
4. ADR-131 expanded valid assigned-auditor relationships but did not replace the legacy role-wide recipient query.
5. Existing tests inspected the authorization function but did not assert that notification producers resolve recipients from assignments.

## Decision

`notify_on_kpi_status_change()` now resolves audit-ready recipients as the deduplicated union of:

- `audit_kpi_level_assignments` for the specific KPI; and
- `audit_kpi_assignments` for the KPI employee.

Recipients must have an active profile and a login account. Notification delivery remains best-effort under POLICY §108. The function is not executable anonymously.

## Consequences

- Unrelated auditors neither receive KPI details nor block business transactions.
- Auditors with either assignment type receive the notification once.
- Existing employee, manager, send-back, and finalized notification paths remain unchanged.
- No historical data repair is needed because failed transactions rolled back atomically.

## Rollback

Restore the prior function body only if the assignment-scoped query causes an operational regression. Doing so reintroduces global disclosure and transaction-blocking risk, so rollback requires incident approval.
