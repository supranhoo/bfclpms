# ADR-173 — Orphaned annual review reviewer succession

- Status: Accepted
- Date: 2026-07-27
- Policy: §AR-ORPHAN-REVIEWER-SUCCESSION

## Context

Reviews stalled indefinitely when a mapped reviewer was deactivated (e.g. 101851 at
`pending_bu` behind inactive BU Head 101969). The organisation-master cascade that should
have repointed them was dead: `tg_business_units_cascade_head_to_ar()` filtered on
`profiles.business_unit_id`, a column that does not exist, so every BU head change failed
with `42703`. There was also no way for an admin to see or fix orphaned stages.

## Decision

1. Fix the BU cascade to resolve membership via `profiles.department_id → departments.business_unit_id`.
2. Add `public.get_orphaned_annual_reviews(uuid)` as the detection SSOT, mirrored in
   `src/lib/annualReview/orphanReview.ts`.
3. Add `public.admin_reassign_orphaned_reviewers(uuid[], text, uuid, text)` for audited bulk repair,
   snapshotting into `public.annual_review_orphan_repair_2026_07`.
4. Add `trg_alert_on_reviewer_deactivation` so deactivating a reviewer/org head raises an
   audit alert instead of silently orphaning work.
5. Ship the **Orphaned Reviews** admin console.

## Consequences

- Succession is org-master first; instance-level repair is the exception path.
- Every repair is reversible from the snapshot table.
- Detection is cheap enough to run on tab open; the console paginates client-side at 25/page
  over a bounded finding set (currently single digits).
