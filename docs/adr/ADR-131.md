# ADR-131 — Auditor↔Reviewer notification guard

**Status:** Accepted (2026-07-21)
**Related:** ADR-112 (bidirectional guard), POLICY §108b/§108d, migration `20260721073800`.

## Context

`can_send_notification_to` (ADR-112) authorised `auditor → anyone` and
`employee ↔ their auditor` (via `audit_kpi_assignments` /
`audit_kpi_level_assignments`). It did NOT authorise the **reviewer chain of
an audited employee** to notify that employee's auditor.

Symptom (Umesh Mehta, 2026-07-21): approving a KPI belonging to Prakash
Chandra Goswami (200549) / Sanjeeb Kumar Jena (101178) — both direct reports
of Umesh — raised toast `not authorized to send notifications to user
f9556e9b-4d12-4374-b290-a397fe1de334` (Auditor03, who holds 374 KPI-level
audit assignments). The notification trigger fired inside the manager's
approve/N-A transaction and rolled back the whole submission.

## Decision

Extend the guard with an auditor↔reviewer branch: if either party audits any
KPI whose owning employee is in the other party's reviewer chain
(reporting_manager, functional_manager, skip, department head, BU head),
allow the notification. Symmetric in both directions. Implemented via a
single joined `EXISTS` over `audit_kpi_assignments` +
`audit_kpi_level_assignments/kpis` against `profiles`/`departments`/
`business_units`.

## Consequences

- Manager / skip / dept-head / BU-head / functional-manager KPI approvals no
  longer fail when the KPI has an auditor.
- No new privileged path: authorisation still requires a concrete audit
  assignment on a KPI owned by someone in the sender's (or target's) chain.
- POLICY §108e records the new edge in the sender-authorisation matrix.
